# gwb-shell

包名 `@godcreator/gwb-shell`，服务 `ctx.gwbShell`。它分两侧：

- **node 侧**——窗格注册服务，插件在自己的 `apply` 里说「我有一个窗格」
- **浏览器侧**——多个 dockview 窗格容器（well，代码模块 `well-hub`；**一张桌面一个、
  容器常驻保活**），把注册表里的每个窗格打开

下游开发入口是随本包发布的 `gwb-shell` 说明书：`skill.read {"name":"gwb-shell"}`。
它统一规定窗格接入、shadcn 官方源码、配套 tokens 与多桌面浮层；正本在
`content/outputs/skills/gwb-shell.mdx`，生成到 `plugins/shell/skills/gwb-shell/SKILL.md`。
`gwbSkills` 通过局部注入登记该目录：这个服务不在时外壳照常运行，服务后加载时补登记，卸载时自动注销。
devkit 只引用这份说明书并提供模板，不复制 UI 规则。

分四个阶段做：前三个阶段与状态栏都完成了；第四阶段的**布局保存**也已完成——每个容器的
布局自动保存、可起名保存布局、点哪套就恢复哪套；**多桌面（保活）已完成**，见下文专节；只剩
导航。

## 怎么用

**注册窗格、报自己的名字**（在你的插件里）：

```ts
export const inject = ['gwbShell']

export function apply(ctx: GwbContext) {
  ctx.gwbShell.registerPane({ id: 'main', title: '我这个窗格', icon: 'flask-conical' })
  ctx.gwbShell.registerPane({ id: 'doc', title: '文档', kind: 'document' })
  ctx.gwbShell.describeSelf({ title: '我这个插件', icon: 'box' })
}
```

一个插件想有几个窗格就注册几个。`icon` 写 lucide 的正名、可以不给，怎么认见
[下文专节](#图标名怎么认)。`client` / `style` 是浏览器侧入口与样式表的 `file://` 地址，给了却不合格的
当场抛错，见[注册时检查什么](#注册时检查什么)。

**注册要说清是工具窗格还是文档窗格**（`kind`，判据见轨迹卡[窗格分两类](/trajectory/2026-09-19-pane-kinds)）：
**工具窗格**（`'tool'`，缺省）**整页至多一份**（判据见轨迹卡[工具窗格全页一份](/trajectory/2026-09-19-tool-single)），打开就是把它显示出来，开在别的桌面上就回那张桌面找它；**文档窗格**（`'document'`）
可以开多份，每份装一个内容。说的是「打开这个动作对它是什么意思」，不是「能开几份」——开几份
仍取决于它**装着几份不同的内容**，见[一个窗格的身份是它装的内容](#一个窗格的身份是它装的内容)。
`kind` 写错按 `tool` 登记、登记那一刻 `gwb.log` 里记一条 warn；`shell.panes` 的回执每条都带它。
它只住注册表、不进面板 params，布局文件里没有它。

**给人看的名字归运行时**（`describeSelf`），不写进包清单——包清单里没人读的字段失效时
没有任何机制会发现。「我是外壳」也不写在包清单里，由 node 端调 `kernel.setShell` 声明。
包清单里没有 `gwb` 字段：本插件提供的服务 `gwbShell` 由源码里给 cordis `Context` 补的那一项声明，`devkit.services`
从装好的包的 `.d.ts` 读它，用法写在 `GwbShellApi` 的文档注释里。兼容哪个内核写在 peer 里内核包
`@godcreator/gwb-kernel-desktop` 的 `^` 范围，插件管理的 `plugin-manager.list` 拿它和运行中的内核比。

**和命令总线的 `register` 一样，这两个都不用自己包 `ctx.effect`**：插件卸载时表上
那几条自动注销。它们仍然返回注销函数，给要提前注销的场景用。

**从界面取表**（在你插件的 client.js 里），两张表分别取：

```js
await args.host.call('shell.panes')
// { ok: true, data: [{ id, title, icon?, client?, style?, entryId, pkg }, …] }
await args.host.call('shell.plugins')
// { ok: true, data: [{ title, icon?, entryId, pkg }, …] }
```

**两张表不合并**：那张的键是 `(entryId, 窗格 id)`、一条条目可以有好几条；这张的键就是
`entryId`、一条条目至多一条。消费方也不同（容器里开窗格用前者，导航列插件名用后者）。

## 图标名怎么认

`icon` 写 [lucide](https://lucide.dev) 的**正名**，kebab-case——lucide.dev 上图标页顶上那个名字
（`layout-grid`、`file-text`、`receipt`）。**全集都认**，不用猜外壳认得哪几个：

- **认得**：标签上画那个图标
- **没给**：标签上画 `#`，不告警
- **认不出**（拼错、改过名的旧名如 `home` 之于 `house`、写成 `LayoutGrid`）：窗格照样登记、标签上画
  `#`，**登记那一刻** `gwb.log` 里一条 `warn gwb-shell`，写明是哪个包的哪个窗格、哪个名字、该怎么写
- `describeSelf` 的 `icon` 同一套认法、同样告警（眼下还没有地方画它）

两侧用同一个判断函数：kebab 名拼成 lucide 的导出名（`layout-grid` → `LayoutGrid`），node 侧拿它对照
名单，浏览器侧拿它从 lucide 全集里取图标：

{/* ref file="../plugins/shell/src/pane-icon.ts" lines="4-14" */}

名单是构建时从**打包进浏览器侧 `client.js` 的那份** lucide-react 生成的（`dist/pane-icons.json`，带版本号），
所以「登记说认得」与「标签画得出」永远是同一份 lucide，产物测试检查两者一致。代价是整个
lucide 全集进了 `client.js`——为什么值、没选的两条路，见轨迹卡
[窗格图标认 lucide 全集](/trajectory/2026-09-17-pane-icons-full-lucide)。

## 身份不由插件自己报

`registerPane` 只收 `{ id, title, icon?, client?, style?, kind? }`，`describeSelf` 只收
`{ title, icon? }`。`pkg` 与 `entryId` 由服务从**调用方的 fiber** 上取：

{/* ref file="../plugins/shell/src/index.ts" lines="439-458" */}

靠的是 cordis `Service` 的机制——方法里的 `this.ctx` 是消费者的 ctx，不是提供方的
（`gwb-data` 的 `owner()` 是同一个做法）。插件没法自报名字，也就没法冒充别人的窗格。

这一点在实际运行中验证时有过直接证据：`shell.panes` 的回执里 `entryId` 是 hello 的
（`home:hello`）而不是 shell 自己的。`registerPane` 登记在 `this.ctx.effect` 上的自动
清理，靠的正是这同一点。

**两样都要，不是只要包名**：同一个包配了两条条目，就是两份独立配置的实例，只有 `entryId`
分得开它们。

## 定义与实例是两回事

|  | 是什么 | 谁产出 |
| --- | --- | --- |
| 窗格**定义** | 注册表里一条，插件说「我有这么一个窗格」 | `pane-registry` |
| 窗格**实例** | 容器里一个 panel，装着不同内容的可以有好几份 | `uniquePanelId` |

`panelIdOf(entryId, paneId)` 是纯函数，同一个窗格必然拼出同一个 id，这个 id 是**基名**；
dockview 的 `addPanel` 遇到重复 id 会**同步抛 Error**，所以实例 id 不能直接用基名，由
`uniquePanelId` 在基名上算：

- 第一份的 id **就是基名**，跟只能开一份的那些窗格长得一模一样——已保存的布局照样对得上
- 第二份起追加 `:2` / `:3`。分隔用 `:` 不用 `#`（`#` 在 CSS 里是 id 选择器）
- 查的是**当下容器里真有哪些**，不是任何一个计数器。所以恢复已保存的布局之后再开
  新窗格也不会重复
- 序号跟 id 一起返回，**不让调用方从 id 里拆**——标题要追加的「(2)」得有个正当来源，而反解
  id 正是这组函数一直禁止的事

## 窗格 id 是个不透明的键

`plugin:<entryId>:<窗格 id>`。实际运行时长这样：**`plugin:home:hello:main`**——四段，
因为 loader 把插件的条目嵌套在 include 那条下面，`entryId` 自带 `home:` 前缀。

那个前缀不能去掉，理由见[遇到过的问题](/docs/walls)。要 `entryId` 或 `paneId` 就从面板的
`params` 里取，那儿本来就分开存着，从来不必反解。

**窗格 id 里不许有 `:`**——注册那一步就拒了。`entryId` 自己带冒号，窗格 id 里再有一个的
话，两组不同的「条目 × 窗格」能拼出同一个基名，而查重会把它当成「已经开着」静默追加一个
`:2`。人看到的是自己的窗格标题莫名多了个「(2)」，源头却在另一个插件的注册参数里。

## 依赖：两个必需依赖

外壳注入的服务只有两样，两样都是**必需依赖（`inject`）**——cordis 的 `inject` 会等到服务就绪才加载本插件，不是建议：
缺 `gwbCommands`，注册表传不出这个进程（下一节是完整理由）；缺 `gwbData`，布局文件没地方存，
布局重启一次就没了。缺哪个本插件就不加载，cordis 在日志里明说它在等谁——而不是加载出一个打不开
窗格、也存不下布局的空外壳。

{/* ref file="../plugins/shell/src/index.ts" lines="115-116" */}

两样都是**基础插件仓的插件**（commands / data），遵守的是全生态那条「本仓 → 基础插件仓」的依赖方向：本仓的
插件把它们列为 peer 依赖，永不反向。

## 为什么命令总线是必需依赖

注册发生在 node 侧，而摆放窗格的是浏览器侧——注册表得经命令传到浏览器侧。内核**一条原生命令都没有**：
页面经 `gwb:command` 发来的命令全走 `ctx.gwbCommands`（命令总线，gwb-commands 插件提供），
内核本体不认识任何插件的命令名。

所以只有一条路：shell 自己注册一条 `shell.panes`。没有命令总线，注册表传不出这个
进程，外壳就是个打不开任何东西的空容器——那种时候不如不加载，cordis 会在日志里明说
它在等谁。

「内核顺手把窗格表带上」这种提议不满足内核准入判据的第一条（内核零 UI 知识）。

## 运行时注册让 openable 少了三样东西

这份 `openable` 的输入是注册表快照，不是「条目表 × **包声明的** `gwb.panes`」。所以三样东西
都用不着：

- **没有 join**——`pkg` 与 `entryId` 注册时就填好了
- **没有过滤**——禁用的插件根本没执行 `apply`、注册不进来；卸载的插件在 effect 清理时自己注销。
  「在表里」就等于「该开得出来」，不需要 `!disabled && !shell` 那两条判断，也就没有它们
  会出的错
- **没有 `canonicalPanelId`**——那是老布局兼容（磁盘上的窗格 id 少一段）用的，这里
  不需要它

## 浏览器侧：容器与窗格

浏览器侧按模块划分，各管一部分：**页面级状态集中在 `well-hub`**（容器注册表、活动桌面、保存
钩子、命令入口、每张桌面上组的最近激活顺序，一份声明接口的对象，面板组件访问不到 App 闭包、
都经它访问）；**开窗格的判断在纯函数 `targetGroup` / `planOpen`**（`openable.ts`，输入是一张
桌面的快照），**执行在 `open.ts`**（挑桌面、聚焦与转正 / 软换 / 开进某一组 / 对半分）；
面板与标签是 `plugin-panel` / `PluginPane` / `GwbTab`；开机
外观装配（注入用户外观样式 + dockview 主题）在 `theme-boot`；向主题插件取启动样式在 node 侧
`startup-style`（`theme.startupCss` 是主题插件可选提供的命令，主题插件没装外壳照常运行）；**两侧共用的命令名在 `protocol.ts`**
（纯模块，两侧各自打包进自己的产物、用同一份常量，不各自复制字符串）；布局文件的形状与判断在
`layout.ts`。

`well-hub` 是模块级单例而不是 React 状态：面板组件表必须是模块级常量（换一个新对象，dockview 会重建全部窗格），
面板组件因此访问不到 App 的闭包；把这些状态放进面板 params 又会随布局一起保存。

`bootShell` 拿到内核给的 `{ host, home, styles, startupCss?, versions }`（问 `shell.env` 来的），接管整页的
根节点：注入三张样式表 → 注入用户外观样式 → 取一次注册表 → **取一次布局文件** → 渲染。文件没有（第一次开机 / 认不出）就从
默认布局开始——默认布局就是「表里有几个窗格开几个窗格」，全放在一个 group 里当兄弟 tab；**工具窗格
全页一份，整页别的桌面上已经开着的不再打开**（`specsForDefaults`，整页开着什么由桌面清单传给 `well-hub` 当场读取——
开机时窗格容器的 onReady 比桌面操作的注入早）。这个默认只发生在三处：第一次开机、布局文件认不出回默认、
状态栏「重置布局」；**运行时新建的桌面不用它，新建时为空**（见下文多桌面节）。

<Diagram name="shell-takeover" title="外壳怎么接管内核的页面">

- shell 插件的 node 侧调 `gwbKernel.setShell(client.js 的地址)`，包在 `ctx.effect` 里，插件卸载时自动撤销
- 内核记下地址，经 `gwb:shell` 推给页面；react 的 importmap 写死在内核的页面入口里，页面一加载就在
- 页面 import client.js，把 `#root` 交给它的默认导出 `mountShell`，留下返回的 `dispose`
- `mountShell` 调 `shell.env` 取 home、三张样式表的地址、启动样式与版本号，交给 `bootShell`：注入样式表 → 注入启动样式 → 取注册表与布局文件 → 给 `<html>` 加 `dark` 类 → `createRoot(#root)` 渲染
- shell 插件卸载时内核推 url 为 null，页面调 `dispose`，外壳同步卸载 React 树

</Diagram>

**卸载是同步的**：内核页面根节点换外壳时先调旧外壳的 `dispose()`、紧接着清空根节点，所以 `dispose`
返回时整棵树必须已经卸载完。准备（异步的那一长段）与挂载 React 树（`createRoot` + `render` 那一小段）
分开：`dispose` 在准备完成之前调用，挂载那段就永不执行；树已挂载就当场 `unmount()`。html 上的类、
根节点上的身份标记、`well-hub` 的命令入口都在挂载那段里设置，一起出现、一起移除。

一个窗格由 `PluginPane` 承载，它是 `mountPane` 契约的外壳这一侧：

<Diagram name="pane-mount" title="一个窗格从注册到关闭">

- 插件在 `apply` 里调 `registerPane({ id, title, icon?, client, style?, kind? })`，`client` 与 `style` 是从 `import.meta.url` 算出的 file:// 地址
- 打开窗格时 `PluginPane` 调 `shell.panes` 当场取这一条的地址
- 有 `style` 就先注入样式表、等它加载完成
- 动态 `import(client)`，取模块导出的 `mountPane`
- 调 `mountPane({ host, shell, pane }, 容器)`，收下 `{ dispose, retarget? }`
- 关窗格时 `dispose` 排进微任务、在 React 提交之外调用，随后释放窗格间总线的句柄

</Diagram>

**样式与模块在同一个 effect 里**：插件的样式表要先注入、而且要等它加载完成再 import，这两件事
有先后顺序的保证；拆成两个 effect 就只能靠 effect 的排列顺序保证「谁先执行谁后执行」。窗格间总线的句柄
也在这个 effect 里取、清理时释放。**拿不到 `dispose` 就报契约不符**，不装作成功——不报的话
关窗格时清理不掉，报出来让写插件的人当场看见。

**插件的 `dispose` 在 React 提交之外调用**（排进微任务，随后释放总线句柄）：`PluginPane` 的
清理 effect 在外壳的提交里执行——关窗格、换外壳卸载整棵树都是——插件若在提交里同步
`root.unmount()` 会被 React 推迟，紧接着清空容器就会先于卸载树执行。移到提交之外之后，插件在
`dispose` 里「同步卸载树、再清空容器」是合法写法。

## 布局保存：自动存 + 起名存，可以恢复

第四阶段剩下的那部分在这里实现。布局文件是 gwbData 里的一份文档 `layout`——**单文档装三样**：
「每张桌面各自的容器布局」（自动防抖保存，每容器一份）、「active」（重启回到哪张）与「存下来的
清单」（人手起名），形状住 `src/layout.ts`（`LayoutDoc` / `DesktopRow` / `SavedLayout`，
纯模块、有单测）。node 侧提供两条命令给浏览器侧读写它：

| 命令 | 干什么 |
| --- | --- |
| `shell.layout.get` | 读布局文件，没存过回 undefined（`readDoc` 对没有的文档回 undefined，**这不是错误、不告警**） |
| `shell.layout.save` | **整份替换**。保存时校验一遍形状——浏览器侧自己的 bug 拼出的坏文件，不能覆盖磁盘上好的那份 |
| `shell.openPane` | 跨插件开一个窗格（任何插件的），见[下文专节](#跨插件开窗格shellopenpane) |

<Diagram name="pane-layout" title="窗格容器、开两份的文档窗格与布局文件">

- 每张桌面一个窗格容器（一个 dockview 实例）；开机只挂载活动那张，别的桌面第一次切过去才挂载
- 同一个文档窗格用不同的 `key` 打开两次是两份实例：第一份的 id 是基名，第二份追加 `:2`；key 与插件的 params 存在面板的 params 里
- 容器布局一变，400ms 防抖后经 `shell.layout.save` 整份替换 gwbData 的 `layout` 文档（desktops、active、saved）；切桌面时立刻保存
- 开机经 `shell.layout.get` 读回，活动桌面的容器用 `fromJSON` 恢复，每份窗格拿回自己的 key 与 params；读不到或认不出就按默认布局打开
- 状态栏「布局」菜单把活动容器的布局起名存进 saved，点哪一条就恢复到活动容器上

</Diagram>

几样东西几个节律：

- **desktops（自动）**：每个容器一变 → `onDidLayoutChange` → 400ms 防抖 → **按当下重拼
  整份** 再写（回调读的全是 ref，迟到的旧定时器写不坏数据）；还没挂载容器的桌面用它已保存的
  那条。重启按 active 回到那个容器。保存失败时状态栏显示「布局保存失败」（点一下重试）；
  外壳被卸载之前先 flush 一次，来不及也只丢最后 400ms 的挪动
- **切换同步 flush**：切桌面先更新 active 再整份写一次，然后才切换显隐——
  `shell.desktop.list` 读的是磁盘上的文件，先写它才不会回上一轮的旧数据
- **saved（人手）**：状态栏「布局」菜单里「把当前布局另存为…」把**活动那个容器**起名存进
  清单，**同名覆盖**（名字就是键，重存就是更新）；点清单里哪条就把哪条 `fromJSON`
  恢复到**活动那个容器**上；行尾 ✕ 删那条。应用某套之后照常自动保存，不用另存。**快照
  与正在用的桌面是两回事**：桌面各自自动存（正在用的），saved 是模板（快照、应用后即弃）
- **文件版本**：现行 v3；读到 v2 当场迁移（current 变第一张「主桌面」、saved 原样带走，
  下一次自动保存写的已是 v3），认不出的版本整份当没有

两条失败路径分开走：**开机恢复不了**（布局文件坏 / dockview 升了版本）回默认布局并 warn，
不阻止外壳启动；**点开某套恢复不了只报错、不回默认**——人明确要的是这一套，悄悄换回默认
布局装作没事比失败更糟。「重置布局」也在那菜单里：清掉**活动那个容器**照「表里有几个窗格开几个」
重新打开——逐个窗格关，不走 `api.clear()`（它内部状态对不上时会抛错）。

## 多桌面：容器常驻保活，浮层挂载点在所在桌面

**语义是保活**——一张桌面一个窗格容器，容器常驻：非活动那张 `visibility:hidden` +
`pointer-events:none` + `inert`，只是不显示、不可交互，DOM、定时器、订阅全活着；
开机只挂载活动容器，其余第一次切到时才挂载、挂载后常驻。为什么是保活、为什么这么藏、
为什么窗格插件契约这么定，整段在 decisions 那页，这儿只写现状。

**可见性是协作式通知**（`shell.onVisibility`）：浏览器的节流（rAF 暂停、后台定时器限流）只作用于整页不可见，
不作用于同一页里被 CSS 藏起来的一块，藏起来的桌面上插件照常运行；同一页里也没有「暂停某棵子树的 JS」的机制，
要强制只能销毁重建，那是另一种语义。所以外壳只通知，停订阅、停渲染、停媒体由插件自己做。通知按桌面 id 分发；
窗格在哪张桌面按 DOM 祖先当场查（`desktop-context`，往上找 `section[data-gwb-desktop]`），不另存「窗格 → 桌面」
的对应表：那张表要跟着开、关、移动窗格同步更新，没同步上也没有任何现象，而容器里的窗格永远是某个桌面 section 的后代。

**切桌面发生什么**，顺序是机制的一部分：

1. 更新 active → 整份 flush 一次（两个容器此刻都活着，`toJSON` 抓到的都是各自
   当下）
2. 显隐交给 React：旧那张藏起来、新那张显示；没挂载过的容器这时挂载
3. 可见性通知（`shell.onVisibility` 的监听函数）→ 焦点接管（给新那张 section 焦点，
   键盘不用先点一下）→ body 检查（查 body 直接子节点里非 #root 的陌生节点，**只报出来
   不删**——插件的浮层该挂载到 `args.shell.portal`，挂载在 body 上的藏不掉，查出来就是没用 portal）。
   **切完隔 500ms 再查**：切桌面常常就是在状态栏的面板、菜单、确认框里点出来的，切换那一刻它们
   还没关（还要走一段退场动画），当场查就把状态栏自己的浮层误报成没用 portal——实际运行日志里从桌面菜单、切换器、
   删当前桌面的确认框切过去每次都报；真没用 portal 的浮层藏不掉，隔一会儿照样在。radix 的焦点护栏
   （`data-radix-focus-guard` 那两个 span，模态菜单开着时插在 body 首尾）与标了
   `data-gwb-status-layer` 的状态栏浮层（「桌面」面板，切完桌面它可能还开着）也不算

<Diagram name="desktop-switch" title="切桌面：容器常驻，浮层跟着自己那张桌面">

- 每张桌面是一个 section：窗格容器，加这张桌面的浮层挂载点（`args.shell.portal`）；不显示的那张加 `visibility:hidden`、`pointer-events:none` 与 `inert`，DOM 与订阅都还在
- 插件的下拉菜单、确认框 portal 到自己那张桌面的挂载点，桌面藏起来时跟着一起藏
- 切到另一张：先改 active 并立刻保存整份布局 → React 切换显示与隐藏（没挂载过的容器这时挂载）→ `onVisibility` 通知两张桌面上的插件、焦点交给新桌面 → 500ms 后检查 body 下有没有没用 portal 的浮层，只报告不删除

</Diagram>

**本桌优先**（判据见轨迹卡[本桌优先](/trajectory/2026-09-19-desk-first)）：实例 id 全页唯一
（`pane.instance` 可当全局键用），但**开窗格只看一张桌面**——有来源开在来源那张，否则开在当前
那张，查重、预览槽、放置位置都在这一张里算；**文档窗格**别的桌面开着同一内容不算命中、也不跳过去。
**工具窗格全页一份**是唯一跨桌面的查重（判据见轨迹卡[工具窗格全页一份](/trajectory/2026-09-19-tool-single)）：
这张桌面没有、别的桌面上有，就到那张桌面激活它（`reveal`）——人在「新建」里点的切过去，插件与命令开的
不切、状态栏提示「『X』在『桌面 N』· 切过去」。除此之外**打开不切桌面**：来源在藏着的桌面上就开在那张
藏着的桌面上，当前显示哪张不变。**运行时新建的桌面新建时为空**（判据见轨迹卡
[新建桌面为空](/trajectory/2026-09-13-desktop-born-empty)）：注册表里有几个窗格与
它无关，窗格由人自己开；容器挂载那一刻就 flush 一次空快照替换文件里的 null——空容器不触发
布局事件，null 留着的话重启会被「null → 用默认布局」恢复成开满窗格的。窗格间总线按条目分组——两张
桌面上同一条条目的窗格在同一组里，跨桌面收得到（这是预期行为，不是缺陷）。

**命令**（node 侧转发的五条）：`shell.desktop.list`（无参数，回
`{ desktops: [{id,name}], active }`，读磁盘上的文件）、`shell.desktop.switch`（`{ id?, name? }`，
id 优先）、`shell.desktop.new`（`{ name? }`）、`shell.desktop.rename`（`{ id, name }`）、
`shell.desktop.delete`（`{ id }`）。容器在浏览器侧，除 list 外都经内核事件入口转发给页面执行，
**回执 ok 只代表转发了**——要确认结果稍等一下再 list。rename / delete 转发之前先用磁盘上的文件
检查 id 在不在（delete 另验「不是最后一张」），认不出当场回错。

### 桌面改名与删除

| 操作 | 发生什么 |
| --- | --- |
| 改名（「桌面」面板里**右键桌面名**，键盘上是 F2；`shell.desktop.rename`） | 桌面名那一行变内联输入框，Enter 确认、Esc 或失焦放弃（Esc 只放弃输入，不关面板）；名字去两头空白，空名不改。改完整份保存一次。右键不用双击：单击是切过去，双击会跟它冲突 |
| 删除（「桌面」面板里那一行的删除钮） | 只剩一张时没有删除钮。**一律先确认**（`deleteConfirmText`）：「删除『X』？」，上面有窗格写「上面 N 个窗格会一起关掉」，空桌面写「这张桌面是空的」；取消什么都不动 |
| 删除（`shell.desktop.delete`） | 同上但不弹确认（调用方已经决定了），只剩一张时回错；回执 `{ ok, relayed, closed }`，`closed` 是转发那一刻页面推送来的清单里那张桌面上的窗格数 |

删掉时上面的窗格**逐个关掉**（插件照常 `dispose`），没挂载过的桌面上的窗格从没加载过插件，连同
已保存的布局一起丢弃；删的是当前桌面就先切到**左边相邻那张**（最左边那张就右边那张，`afterDelete`）。
删除而不合并，是用户定的：窗格里的东西存在各插件自己那里，关掉丢的只是窗格的摆放位置，确认框挡住误删；要留下
哪个，删之前先送到别的桌面。

### 送到别的桌面、拉到本桌

入口：把窗格拖到「桌面」面板里的另一张桌面上（面板里的窗格行，或直接从桌面上拖标签，见
[「桌面」面板](#桌面面板所有桌面与上面的窗格)）、标签右键「送到 ▸ 桌面 X / 新桌面」、`shell.pane.send`。dockview 没有
跨实例搬面板的接口，所以**送到是一次关闭加一次打开**（`sendPane`）：

1. 取这一份的定义、key、插件自己的那部分参数与标题，两张桌面有没挂载过的先在后台挂载（不显示）
2. 在源桌面关掉它（插件 `dispose`）
3. 在目标桌面按 `planSend` 开：**工具窗格**目标桌面已有同一定义、同一 key 的（老版本留下的多份）就只激活那一份；
   否则按目标组规则（没有来源：最近用过的同类组，否则活动组，桌面空就新建一组）开一份**正式**
   标签——预览不带过去，文档窗格目标组里有同一内容也照开
4. **当前桌面不变**，状态栏显示一句「已送到『X』· 切过去」（10 秒），点「切过去」才切；拖放或菜单里
   按住 Shift、或命令带 `follow: true`，送完跟过去

标题按 `carriedTitle` 带过去：插件自己改过的原样带过去，还是定义的缺省标题（含「(n)」）就按新序号
重算。「送到新桌面」先建一张空桌面（缺省名「桌面 N」，要改名右键桌面名）再照上面送，同样不切
过去——建的时候**不保存**：布局文件里那时写的会是 null，重启就被「null → 用默认布局」开满窗格（轨迹卡
[新建桌面为空](/trajectory/2026-09-13-desktop-born-empty)那个问题），紧接着挂载容器时的空快照
flush 才写进去。

**插件的状态只靠参数带过去**：步骤 2、3 之间插件被重新挂载，滚动位置、打到一半的字这类东西，
插件想保住就得放进 `setPaneContent` 的参数里。这是文档窗格要上报内容的第二个理由。

**拉到本桌**：在「桌面」面板里把别的桌面上的窗格拖到当前桌面上——等于送到当前桌面，送到之后
激活它，不涉及切桌面。

**只有这几种动作会切桌面**：点「桌面」面板里的一张桌面，或别的桌面上的一个窗格；在「新建」里点
开在别的桌面上的工具窗格；点状态栏那句「… · 切过去」；新建桌面（状态栏、`shell.desktop.new`）；删除
当前桌面；`shell.desktop.switch`；`shell.pane.focus`（窗格在别的桌面时）；送到时按住 Shift 或
`shell.pane.send { follow: true }`。别的一律不切，包括插件的 `openPane`、`shell.openPane`（要开的工具
窗格在别的桌面上时只提示）、「新建」里开新的那些、「送到新桌面」。

## 窗格插件拿到的 args

这是**窗格插件契约的正本**（内核只定 `bootShell`，`mountPane` 的 args 由外壳定）：

```ts
mountPane({ host, shell, pane }, container) => { dispose(); retarget?(params) }
```

| | 是什么 |
| --- | --- |
| `host.call(command, args?)` | 命令通道，走到宿主分发再原路回 |
| `shell.openPane(paneId, { key?, params?, preview?, placement? })` | 打开**本插件**的另一个窗格。**来源自动就是调它的这一份**：新窗格落在它旁边、开在它那张桌面上，从不切桌面；`placement` 缺省 `'auto'`（按目标组规则），`'side'` 开到旁边 |
| `shell.setPaneTitle(title)` | 改这个窗格标签上的标题 |
| `shell.setPaneContent({ key, params?, title? })` | **上报这个窗格此刻装的内容**：原地换了内容之后上报一次，外壳改这一份的 key（与参数、标题），不软换、不重新挂载。见[下文专节](#上报内容setpanecontent) |
| `shell.keepPane()` | 把这个窗格留住：它不再是预览窗格 |
| `shell.bus` | 窗格间小总线，`emit(type, detail?)` 与 `on(type, fn)` 回注销函数 |
| `shell.portal` | 本窗格所在桌面的**浮层挂载点**：插件里 radix Portal 的挂载点设成它，桌面切走浮层跟着一起藏。不在桌面体系里时是 `document.body`（radix 缺省），插件不必判空 |
| `shell.onVisibility(cb)` | 本窗格所在桌面的可见性：切走收 `false`、切回收 `true`，**注册即回一次当下值**，回注销函数。协作式降级——插件拿它停订阅 / 停渲染 / 停媒体，外壳只通知不强制 |
| `pane.id` | 这个窗格是本插件的哪个窗格（注册时给的那个 id） |
| `pane.kind` | 外壳把它当哪一类加载的：`'tool'` 或 `'document'`（注册时说的，不说就是 `'tool'`） |
| `pane.instance` | 这**一份**的唯一键。开两份时两份的这个值不一样；**全页唯一**（可当全局键用） |
| `pane.params` | 挂载这一刻这一份装的那份参数。没传就没有这一项 |

**只开得了自己那几个窗格**：`entryId` 由 `PluginPane` 造这个对象时闭包绑定，插件报不出别人的
条目——跟 `registerPane` 不收身份是同一条理由。命令里另有一条跨插件的入口，见下节。

### 类型从 `@godcreator/gwb-shell/pane` 引

窗格插件写 `mountPane` 用到的类型都由外壳导出，插件用 `import type` 引，不在自己代码里手写、不用 `as`
转成它们（规矩见生命周期插件仓 `gwb-lifecycle-plugins` 的 `docs-site/content/docs/rules/interaction.mdx`「类型放在提供方那边」）：

```ts
import type { PaneArgs, PaneHandle } from '@godcreator/gwb-shell/pane'

export function mountPane(args: PaneArgs, container: HTMLElement): PaneHandle { … }
```

| 类型 | 对应 |
| --- | --- |
| `PaneArgs` | `mountPane` 的第一个参数 `{ host, shell, pane }` |
| `PaneHandle` | `mountPane` 的返回值 `{ dispose(); retarget?(params) }` |
| `HostBridge` | `args.host` |
| `ShellBridge` | `args.shell` |
| `OpenPaneOptions`、`Placement` | `shell.openPane` 的第二个参数，与其中的 `placement` |
| `PaneKind` | `pane.kind` |
| `PaneContent` | `shell.setPaneContent` 的参数 |

入口文件是 `plugins/shell/src/client/pane-api.ts`，只有 `export type`；类型本身定义在 `src/client/types.ts`、
`src/openable.ts`、`src/panels.ts`。改这几个类型就是改外壳对插件的接口。

**子路径 `./pane` 只有类型**：`build` 脚本用 `src/client/tsconfig.pane-types.json` 只输出声明
（`emitDeclarationOnly`）到 `dist/types/`，`package.json` 的 `exports["./pane"]` 只有 `types` 条件。
插件 `import type` 它，构建产物里这一句整句消失；写成按值 import，esbuild 构建时报这个子路径没有导出。
它引用到的文件里没有包名 import，调用方的浏览器侧类型检查不用为它多列依赖。这几点由产物测试
`plugins/shell/tests/artifact.test.ts` 里「子路径 ./pane」那一组检查。

**不从主入口 `@godcreator/gwb-shell` 导出**，两个原因：

- 主入口的声明 `dist/index.d.ts` 是 node 侧的：它引 `cordis`、内核包 `@godcreator/gwb-kernel-desktop`（接口类型）、`@godcreator/gwb-commands`、
  `@godcreator/gwb-data` 的类型，还带着给 cordis `Context` 加字段的 `declare module 'cordis'`。浏览器侧 `import type`
  主入口，这些包全部进入浏览器侧的类型检查，调用方得把它们都列进 dev
- `ShellBridge.portal` 是 `HTMLElement`，node 侧 tsconfig 没有 DOM 类型库，主入口转导出这几个类型当场报 TS2304；
  给 node 侧加上 DOM，node 侧代码写 `document` 也不再报错

选型经过见轨迹卡[窗格入口类型走子路径](/trajectory/2026-09-24-pane-types-subpath)。

## 跨插件开窗格：`shell.openPane`

插件手里的 `args.shell` 只开得了自己那几个窗格（上一节）；跨插件的场景要打开**别人的**窗格——第一个
需求方是单元文件夹窗格里启动站点的按钮：点了要打开站点插件的预览窗格，而页面上

多窗口时各页各自执行，与 desktops 那几条相同。

`pane.instance`），新窗格落在它旁边、开在它那张桌面上；页面上哪张桌面都找不到它，就当没有来源、
开在当前桌面，console 里一条 warn。`placement` 只认 `'auto'` / `'side'`，别的值当场回错。

## 一个窗格的身份是它装的内容

一句话：

> 一个窗格开几份，**是因为它们装着不同的东西**，不是因为谁给过它开第二份的权限。

插件开窗格时给一个不透明字符串 `key`（不给等于空串，所以「没给 key」不是特例），外壳只拿它
去已开的几份里找，一个字都不解释。开一个窗格分两步，都在纯函数里：

**先算目标组**（`targetGroup`，判据见轨迹卡[目标组取代按份数分档](/trajectory/2026-09-19-target-group)）。
`placement: 'side'`：基准组是来源所在的组（没有来源用活动组），它右边紧挨着有一组就是那组，
没有就把基准组对半分、右半边是新组。`'auto'`（缺省）按顺序取第一个成立的：

1. 来源与要开的是**同一个窗格定义** → 来源所在的组
2. 这张桌面上有**最近用过的同类组**（最近被激活、装着这个窗格的实例）→ 那一组
3. 有来源 → 照 `side` 算
4. 有活动组 → 活动组
5. 桌面是空的 → 新建一组

「右边紧挨着」按组的矩形判（左边沿在基准组右边沿 16px 内、竖向有重叠，好几组都挨着取重叠
最多的），所以嵌套成什么样都一样判。

**再查重、出判断**（`planOpen`）：

```
want = options.key ?? ''

工具窗格：这张桌面任何一组里有同一个窗格、key === want 的 → 激活它（在哪组就在哪组）
          本桌没有、别的桌面上有                         → 到那张桌面激活它（reveal；切不切归调用方）
文档窗格：只在目标组里找                                   → 激活它
  找到的是预览窗格、这次是正式打开                          → 顺带转正
没找到、要了 preview：目标组里有这个窗格的预览窗格 → **软换**它（params 整份换成新内容）
                      没有                        → 在目标组开一份新的，标成预览窗格
没找到、没要 preview                                       → 在目标组开一份新的正式窗格
认不出那个窗格                                             → 什么都不做，但话里带得出是谁要开什么
```

哪一类看注册表：`kind` 跟着窗格定义走（`OpenableSpec.kind`），开窗格时从当场取的注册表里带上。

判断全在 `planOpen` 里，执行那侧只剩「按 kind 分派」——**有一条分支在实际界面上点不出来**
（传的参数用了保留键，得专门写一个故意传错参数的插件才走得到），这也正是它必须是纯函数的理由。

`planOpen` 的输入是**一张桌面的快照**（`Desk`：各组按顺序的标签、活动标签、组的矩形，加这张
桌面上组的最近激活顺序），由执行侧从那张桌面的容器当场读取；别的桌面开着什么不进快照。唯一跨
桌面的是实例 id 查重（`uniquePanelId` 问所有容器）——第一份仍然就是基名，第二份起追加 `:2`，
**序号按全页算**：别的桌面占用的序号不能用。「最近激活顺序」只在运行时记（组被激活、拖放落进
哪一组都算，在恢复布局之后才开始订阅），不保存到磁盘，整页重载后从空开始。

### 预览窗格：至多一份，可被替换，开始用就转正

照 VS Code 那套语义，**实现是我们自己的**：dockview 的 PinnedTabs 是付费模块，而且它的
pin 管的是排序与溢出，跟「别换我的内容」不是一件事。

| | |
| --- | --- |
| 怎么进 | 插件开窗格时 `preview: true`。**每一组里同一个窗格的预览窗格至多一份**：两组可以各有一个，不同窗格的预览窗格同组并存 |
| 被替换 | 下一次 `preview: true` 打开、落在同一组、内容不同 → **原地换内容**（`retarget`），位置不动、窗格数不变。别的组的预览窗格不碰 |
| 怎么转正 | 插件调 `shell.keepPane()`、人**双击标签**、标签菜单「保持打开」、以正式方式打开命中它、「在旁边再开一份」它。最后都是同一个动作：把 `preview` 从这一份的 params 上删掉 |
| 标成什么样 | 标题前面**一个小空心圆点**（边框走 currentColor，带 `aria-label`）。**不用斜体**——中文没有真斜体，浏览器画的伪斜体很难看 |
| 没有的动作 | **正式窗格变不回预览窗格**。VS Code 也没有 |

「每组一份」而不是「每桌一份」，判据见轨迹卡[预览窗格每组一个](/trajectory/2026-09-19-preview-per-group)。

**标例外不标常态**：预览窗格至多一份，正式窗格可以很多，所以记号打在预览窗格身上、正式窗格一个
像素都不变。

**记号是形状不是深浅。**「标题颜色再淡一些」不行：**未激活的标签本来整体就是 muted 前景色**，
在未激活的标签上再调淡等于没标，而预览窗格多数时候恰恰不是激活的那一个。圆点靠的是有没有
这个东西，激活未激活都认得出；颜色交给 currentColor，跟着标签四态走，不用自己配一套。

插件该在「人真的开始用这个窗格」那一刻调 `keepPane()`（开始编辑、改了什么），**不是挂载时就调**
——挂载时就调等于这个插件没有预览窗格。它是幂等的：已经是正式窗格时那一下什么都不做（连一次
params 变更都不发，不然每次击键都要引起一轮重渲染与一次布局保存）。

### 换内容：软换与硬换

外壳换掉这个窗格的 params 之后，**插件给了 `retarget` 就调它（软换），没给就卸载后重新挂载（硬换）**。
判的是句柄上有没有那个函数，不是插件说了什么：

```ts
mountPane(args, container) {
  const view = mount(args.pane.params)
  return {
    dispose: () => view.destroy(),
    // 有它就是软换：这棵树、这份滚动位置、人正打到一半的字全留着
    retarget: (params) => view.go(params.root),
  }
}
```

硬换是**正常路径**，不是契约不符：简单的插件不必为此写一行代码，代价是这个窗格的内部状态跟着
重来一遍（`hello` 的 `counter` 故意不给 `retarget`，验的就是这条）。

处理这件事的是 `PluginPane` 的第二个 effect。两处要注意，都是实际运行时会静默出错的地方：

- **比的是 params 的稳定序列化，不是对象引用**（`paramsKeyOf`：键先排序再 `JSON.stringify`）。
  面板 params 每轮渲染都取出一个新对象，按引用比等于每轮都算「换了」；而 params 本来就要求
  可 JSON 序列化。挂载那个 effect 的依赖数组里**故意没有 `paneParams`**，理由同上
- **插件还没挂载完成时什么都不做**：挂载流程读的是 ref、读到的一定是最新那份。这时候触发重新挂载
  只会把正在进行的那次挂载白白打断

### 上报内容：`setPaneContent`

软换与硬换是**外壳换内容、通知插件**；反方向是插件自己在窗格里换了内容（点链接原地跳转、
后退前进）——外壳看不见，得插件上报一次：

```js
// 原地跳到了另一块
args.shell.setPaneContent({ key: 'lib:b', params: { root: 'b' }, title: '第二块' })
```

外壳只改**这一份**的面板 params：key 换成新的；给了 `params` 就**整份替换**插件自己的那部分（保留键
移除并告警，旧的那部分多出来的键删掉）；给了 `title` 等于顺带 `setPaneTitle`。之后照常保存，整页
重载回到上报的内容。**不调 `retarget`、不重新挂载**——内容已经在插件手里换好了：`PluginPane` 记着
「插件手上此刻是哪份参数」，面板 params 换成插件自己报的那份时，那个软换 effect 认得出来、
什么都不做。预览窗格上报之后仍是预览窗格，转正归插件自己调 `keepPane`。

插件按有没有这个函数判断外壳支不支持上报（`typeof shell.setPaneContent === 'function'`）；旧版外壳上
没有这个函数，插件就不上报（key 与参数停在打开那一刻）。

### 开出来的几份靠 `params` 彼此不同

`key` 解决「这是不是同一个窗格」，`params` 解决「这一份里装的东西长什么样」：

```js
args.shell.openPane('doc', { key: 'a.md', params: { file: 'a.md' } })
// → 那一份的 mountPane 拿到 pane.params === { file: 'a.md' }
// 再点一次同一个 key：聚焦那个窗格，不新开也不换内容
```

**它跟着布局保存**：这份参数并进面板 `params`，`api.toJSON()` 原样带上、整份写进
gwbData 的 `layout`，`fromJSON` 再原样传回来——重启之后那一份拿到的还是当初那一份，
插件不用自己存一遍。

代价就写在这条好处背面：**必须可 JSON 序列化**。函数、DOM 节点、类实例塞进去，症状是
重启之后才出现的「参数变形了」。

**保留键 `pluginKey` / `entryId` / `paneId` / `icon` / `key` / `preview` 归外壳**：插件传了会被
**移除**并出一条 console 警告——不是覆盖，也不是静默丢弃。移除而不是用外壳的值覆盖，是因为
「悄悄用了另一个值」这种现象从插件那头查不回来；告警之后插件当场看得见自己传错了。反方向同理：
插件拿到的 `pane.params` 也不含这几个键，插件不该认识外壳内部的身份字段。

后两个（`key` / `preview`）进这张名单是有代价的：**插件从此不能拿这两个名字当自己的参数名**。
换来的是身份跟着面板 params 一起保存——整页重载之后外壳照旧认得出哪个窗格装着什么、哪个窗格是
预览窗格，不用另存一份数据。

**不作用于聚焦**：走到聚焦时那个窗格装的本来就是这份内容（key 对上了），它早已挂载、
`mountPane` 已经拿过一次参数。这时改面板 `params` 只会让磁盘上的文件跟界面上正在运行的那份对不上
——要换内容走的是 `preview` 那条（软换），那条会连着通知插件。

**表当场取、不用快照**：插件可以在运行中加载，后加载的插件在快照里没有自己。取表是一次本地 IPC，
而调用方全是 click 回调、没人等返回值。

**总线按条目分组**，所以同一条条目的几个窗格——含同一个窗格的两份——在同一组里。一个窗格卸载时
自己注册的监听函数要全部注销，理由见[遇到过的问题](/docs/walls)。

总线不用 `window` 上的 CustomEvent：那是整页共享的命名空间，两个插件挑了同一个事件名就会收到对方的事件，
而窗格收到了别人的事件这种现象查不出来源；按条目分组之后，事件名只在本条目内有效。也不用 `EventTarget`：它把
监听函数抛出的异常交给全局错误处理，而这里要的是一个插件写坏了不影响同组的其他窗格，所以异常按监听函数隔离，
就地记一条带条目 id 的 console.error。分组按引用计数存在，最后一个窗格释放时整个删除——留着空分组的话，同一条目
关掉再开会收到上一轮注册的回调。`inspect()` 只给验收用：总线不通的症状是另一个窗格没反应，这跟插件没发、事件名
写错、两个窗格不在同一组分不开，要看分组的状态才能定位。

**新窗格开进目标组，插在活动标签的右边**：dockview 的 `openPanel` 不给 `index` 就追加到组末尾，
所以 index 由 `planOpen` 算好（活动标签的位置 + 1，说不出活动标签就追加）。**摆放永远带参照**：
只给 `direction` 的 `position` 在 dockview 那头是 `AbsolutePosition`（`_doAddPanel` 里
orthogonalize 那个分支），放在整个容器的边上、所有组重新分配宽度，外壳不走那条。

**要新建组时只把基准组对半分，别的组不动**：先把新窗格当**不激活的**标签开进基准组，再
`moveTo` 到它右边——这是 dockview 拖放那条路（`dropSizing` → `Sizing.Split`），只切参照组一半。
`addPanel` 带参照带方向那条不给尺寸时同一排全部均分，给 `initialWidth` 时从这一排最右那组扣；
基准组在一列里时 dockview 把它包进新分支，还会少掉一份组间缝的高度，分完用 `splitHeightFix` 算出的高补回去。

**软换是 `api.updateParameters`，而它是合并、不是替换**：dockview 那头做的是 `{ …旧, …新 }`，

## 状态栏

容器底部那条，**它是唯一不进窗格系统的东西**——也正因如此它能处理「窗格全部关掉了怎么办」，
也正因如此它是桌面切换器唯一合理的位置：它不属于任何一张桌面，位于所有容器外面
（z 也更高，模态遮罩盖不住它）。布局是两行：桌面区 `flex-1 min-h-0`，状态栏 `flex-none`。

**`min-h-0` 少不了**：flex 子项默认 `min-height: auto`，容器里内容一高就把状态栏挤出屏幕。

左边三段是能动手的，右边三段是只读的环境与全局开关，外加告警与提示：

| （告警）**布局保存失败** | 只在保存失败时出现，点一下立刻重试 |

**版本各自问出处**：内核版取 `gwbKernel.version`——内核读自己包清单报的，外壳不自己调 `app.getVersion()` 去猜（从源码启动内核时那是别的包的清单）。安装包版本不显示：内核不报它（判据见轨迹卡[状态栏不再显示安装包版本](/trajectory/2026-09-25-statusbar-drop-launcher)）。外壳版读本包清单；
Electron / Node / Chromium 是主进程的 `process.versions`。这几样在 node 侧回应 `shell.env` 时拼好，
浏览器侧只负责显示：

{/* ref file="../plugins/shell/src/versions.ts" */}

**刷新是整页 reload，不是外壳内部重建**：渲染层那条 boot 流程（onShell 收外壳地址 →
bootShell → 取注册表 → 取布局文件 → 恢复）原样重新执行一遍；内核那部分与页面加载无关（IPC
句柄在主进程启动时注册，宿主进程也在那边运行），reload 对它只是一次重新连接。装了新插件、
启停了插件之后点它，比重启整个应用开销小。

### `shell.reload`：同一件事的命令版

那个「刷新」按钮还有命令版本——`shell.reload`，无参数，给热升级之后的调用方用：插件管理窗格拿到
`plugin-manager.update` 的成功回执后调它，agent 经 MCP 升级完也调它。插件管理自己不调。node 侧换成新版本之后，开着的窗格用的
仍是旧的 client.js，浏览器已经 import 过的模块不会重新加载，只有整页重载能让页面重新 import 到新东西。
经页面调它时，页面在回执送回之前就开始重新加载，调用方收不到回执。

插件运行在 Electron **主进程**里，`import('electron')` 拿得到 `BrowserWindow`——开窗、重载全归插件，
内核一样都不替插件做。三处要注意：

- **取窗口列表抽成可注入的 deps**。测试里没有 electron，纯逻辑那部分（没窗口怎么回、有几个窗口就
  reload 几个）传入一份假的就能测；实际运行用的那份 `electronWindows()` 不在 Electron 里就 reject

  记在[遇到过的问题](/docs/walls)
- **说明符走变量**，不让 tsc 去解析 `electron` 这个模块——本包不依赖它的类型（那要把整个
  electron 装进插件的 devDependencies，只为一个方法名），运行时它就在主进程里

**没有窗口回 `ok: false`**，不静默回成功——回成功的话调用方以为界面刷了，其实什么都没发生。

**启动与切换分开**（判据见轨迹卡[启动器与切换器分开](/trajectory/2026-09-19-launcher-switcher)）：
「新建」只管开一个新的，「桌面」面板只管切到已开的。一个列表同时干两件事，对文档窗格就说不清点下去
是开新的还是切过去。

**启动器的判断是 `planLaunch`**（跟 `planOpen` 同住 `openable.ts`）：落点是**活动组**、不走
「最近用过的同类组」；文档窗格不查重（key 空串、不带参数，插件画它的默认内容）；工具窗格当前桌面
已有（空 key）就激活、别的桌面上有就 `reveal`（启动器是人点的，切过去），是预览就顺带转正。
**行尾那句问的就是 `planLaunch` 自己**（`launchGoesTo`：点下去会走成激活当前桌面那份——「→ 当前桌面」、到别的
桌面激活——「→ 桌面 X」、还是开一份新的——「＋」），不是「这个窗格有没有开着」——另写一份判断就有了两处
依据，两处不一致时没有任何现象，只是行尾开始显示错的。写的是**动作**不是状态：写「当前桌面已开」「在『X』」这类状态，
人还得自己推断点下去会怎样。去已开的那几行左边一道色条（像任务栏给运行中的程序加标记），扫一眼就
挑得出；不用灰色（灰色是「点不了」，这几行照样点得动），不用圆点（预览窗格已经用空心圆点了）。清单
每次点开当场取，所以运行中新装的插件不用刷新就在。

**启动器选了之后不关**（用户定的：常拿它一连开好几样）：`onSelect` 里拦下 radix 的「选中就关」，开完
静默重新读取一次清单（旧清单先留着，不闪「正在读取注册表…」），点外面或 Esc 才关。它是模态菜单，焦点锁在里面，
切桌面时焦点被挪走也不会让它关掉；点了开在别的桌面上的工具会切桌面，那时菜单还开着，所以它也标了
`data-gwb-status-layer`，body 检查认得。

### 「桌面」面板：所有桌面与上面的窗格

切换器与桌面清单是**同一个面板**（判据见轨迹卡[桌面面板](/trajectory/2026-09-19-desk-panel)）：面板里只摆
桌面与各桌面上的窗格，照桌面本来的顺序（`desktopSections`，当前那张标「当前」，不提到最前），行内
没有关闭、送到、拉到本桌这些钮——关窗格在标签上，送到与拉到本桌是拖拽：

| 操作 | 发生什么 |
| --- | --- |
| 点一张桌面 | 切过去 |
| 点一个窗格 | 激活它；在别的桌面就切过去再激活（没挂载过的先挂载） |
| 右键桌面名 / F2 | 改名（见[桌面改名与删除](#桌面改名与删除)） |
| 删除钮 | 先确认再删（确认框叠在面板上面）；只剩一张时没有 |
| 把窗格行拖到另一张桌面上 | 送过去；拖到当前桌面上就是拉到本桌；拖到「新建桌面…」上就是送到新桌面。拖到目标上悬停时显示底色，放回它本来那张不接（`acceptsDrop`）。放下时按住 Shift 就跟过去 |
| 从桌面上拖一个标签到状态栏「桌面」项上 | 停 500ms 面板自己弹开（弹簧载入），再放到哪张桌面上同上；没停够就放开，面板不弹开 |
| 什么时候关 | **只有点面板外面或 Esc**：上面这些做完面板都留着（用户定的：这张面板常拿来来回切） |

radix 的弹出面板缺省还有一条「焦点移出去就关」：切桌面时外壳把焦点交给新桌面、激活窗格时 dockview
也会挪焦点，不拦的话面板照样会因此关掉——所以 `onFocusOutside` 拦掉，只留「点外面关」。

是弹出面板（shadcn `popover`）不是下拉菜单：菜单的规矩是点一项就选中关掉、按键拿去做首字母跳转，
跟改名输入框、拖拽都冲突。改名时 Esc 只弃输入：radix 的 Esc 监听在 document 的捕获阶段，比输入框
先收到，所以面板的 `onEscapeKeyDown` 在改名 / 起名时拦下来。

**拖的是哪个窗格**（`pane-drag.ts`）：面板里的行在 dragstart 时记在模块里——HTML5 拖拽在 dragover
里只看得到数据的类型、读不到内容，而「这张桌面接不接」在 dragover 里就得答；桌面上的标签是 dockview
自己的拖拽，它把 `{ viewId, groupId, panelId }` 放在页内单例里（`getPanelData`，外壳的 client.js 里只有
一份 dockview，单例就是同一个），drop 在 dragend 之前，放下那一刻还读得到。整组拖（组头，`panelId`
为 null）不算。

### 菜单 portal 到哪都有样式——别把前缀隔离改回选择器限定范围

是不是有人把前缀隔离又改回了选择器限定范围。判据见样式与组件的[隔离靠名字，不靠位置](/docs/styles#隔离靠名字不靠位置)。

## 两张样式表，规矩不同

**前缀隔离是怎么回事、值与规则为什么一个共享一个隔离、组件为什么各拉各的——原理全在
[样式与组件](/docs/styles)那一页**，这儿只记外壳自己那两张表的规矩。

| 产物 | 隔离方式 | 装什么 |
| --- | --- | --- |
| `./style.css` | **类名前缀**——类选择器一律 `.shell\:` 开头 | 外壳自己 JSX 的 Tailwind 类 |
| `./dockview.css` | **没有，也不需要** | **裁过的** dockview 基础规则 + 我们自己那套 theme |

后者做不了任何隔离，两个理由：它管的 `.dv-*` 类名不经我们的手（改不了名，也就加不上
前缀），而且 portal 元素可能挂载在 `body` 下——包进 `:where(…)` 一条都匹配不上。前者的前缀隔离则
**跟 DOM 位置无关**，所以状态栏那两个 portal 到 `body` 的菜单照样有样式。

### 它的 18 套主题一套都不用

`.dockview-theme-gwb` 是**唯一的主题来源**，不是在谁的基底上打的补丁。要它的布局与拖放，
不要它的审美——「看着不像 shadcn」的来源全在主题里，而主题跟引擎是分得开的：形状与配色
全走 CSS 变量（`.dv-tab` 自己只有一句 `flex-shrink: 0`）。

「不用基底主题就有 682 处 `var()` 读空」不构成反对理由：读空的前提是我们没定义，而这条路要做的
正是全定义。量下来裁剩的基础规则引用 **54 个**不同变量，
`dockview-theme.css` 定义了 71 个（多出来的是企业模块那批，全定义好过维护例外清单）。

### 因此原表能裁掉三分之二

`build.ts` 用 postcss 解析原表，**凡是选择器带 `.dockview-` 的规则整条剔掉**；一条规则有
几个选择器时只删掉属于他们的那几个。实测原表 154,125 字节裁到 50,686，**省 103,439**；
拼上我们那套 theme 之后产物是 59,422。

被裁的不只是 18 套配色，还有 `.dockview-spaced` 这个 modifier——圆角与间距的实现规则原本
在那儿，所以我们那张 theme 表把用得上的**复制了一份**：组的圆角、标签块的圆角与外边距靠这几条
作用到 DOM 上。

### 容器的样子：每组一张卡片，浮在容器底色上

每个组是一张卡片：1px 描边、圆角取令牌 `--radius`、底色 `--background`。组与组之间留 8px 空隙
（dockview 的 `theme.gap`），整个容器外圈再留 8px，空隙里露出的是比卡片暗一点的容器底色
`--gwb-well`（从 `--background` 用 `color-mix` 调暗，亮暗主题跟着变）。组之间不画分隔线
（`--dv-separator-border` 透明）：空隙本身就是分隔，再画一道线就是两种分隔手法叠在一起。

外圈的 8px 只能是 `.dv-shell` 自己的 padding。dockview 用 ResizeObserver 量这个元素的 contentRect
来定网格尺寸，padding 按定义不算进 contentRect；加在 `.dv-shell` 与 `.dv-grid-view` 之间的任何一层都
不行——`BaseGrid.layout` 会把网格根的尺寸直接写成 `.dv-shell` 的 contentRect，中间那层的 padding 缩不掉
它，溢出的部分被裁掉（最右、最下的描边看不见），还会让 `.dv-view` 出现滚动条。网格根自己要透明：
`--dv-group-view-background-color` 同时涂在网格根和每个组上，网格根不透明就把容器底色整个盖住。

标签是卡片头上的浅色圆角块（6px）：标签条高 32px、标签 26px、字号 13px。标签的底色、字色和悬停
效果全部由外壳的标签组件 `GwbTab` 画，dockview 那四个「组是否活动 × 标签是否显示」的颜色变量都设成
透明与继承——它只认这四种静态组合，表达不了悬停，让它画一半只会跟 `GwbTab` 冲突。dockview 基础规则里
标签的 `padding` 是字面值不是变量，所以主题表单独把它归零。

拖放落点的底色用中性灰（`--foreground` 混 12%），不用强调色：强调色会让「放到这里」看起来像「这个组
被选中了」。浮动组不画外框，因为里面的组已经有自己的 1px 描边。

滚动条的样式也写在这张表里，而这张表不限定选择器范围，所以对整页生效，插件里的滚动容器也用这一套：
8px 细条、圆角滑块、没有上下箭头按钮、轨道透明，滑块颜色从 `--foreground` 混出来，亮暗跟着变。

**为什么敢裁**：基础规则与主题规则交错着，裁错一条的症状是某个交互没样式——用内置主题时
没有可靠的切分依据，只能整张带上；外壳一个内置主题都不用，整类可以按选择器整体剔除，
风险从「猜」变成了「解析」。

裁表是**每次构建都会执行的代码**，写坏了两头都不报错（裁多了某处没样式，裁少了他们的主题
悄悄覆盖我们的值），所以产物测试检查两条：一条 `.dockview-` 都不许剩、基础规则的字节
数得在 50–70KB 之间。

### 亮暗不靠换类

`--dv-*` 全部引用令牌，令牌跟着 `html.dark` 变，容器、标签条、插件里的按钮一起变，**一行都不用
重新构建**。实际逐处量过。

**一个例外：`--dv-floating-box-shadow`**。dockview 给的默认值在暗底上量出来是
`rgba(0,0,0,0.12)`，浮动组整个失去立体感。这个变量的语义**本来就跟明暗有关**（阴影就是
影子），所以表里给暗色单独写一条规则 `.dark .dockview-theme-gwb`。

这不违反上面那条：**换的不是主题类，是我们自己这张表按 `.dark` 给不同的值**——跟令牌表
本身 `:root` / `.dark` 两套值是同一个做法。往后再发现哪个变量在暗色下不对，照这条补。

### 升级 dockview 之后要核对一次变量全集

62 个全由我们给，它新增一个我们就漏一个，而漏了是**读空、不报错**。核对方法与「为什么
不做成构建期检查」见[遇到过的问题](/docs/walls)，主题怎么交给它（加在 `<html>` 上是没用的）
也在那儿。

## 为什么不用 dockview 自己的注册

**下一个人一定会问**：dockview 有 `components` 表，为什么还要 `pane-registry`？

因为那两样管的不是一回事。dockview 的 `components` 是「component 名 → React 组件」——
我们全部窗格都映射到**同一个** `plugin` 名上；而 `pane-registry` 是「有哪些窗格值得存在」。

它替代不了，差的三样是根本性的：

- **跨进程**——dockview 的注册接口全是同一个 JS 堆里的对象引用，没有任何可序列化的形态；
  我们的注册方在 node 进程、消费方在浏览器
- **未开也在表里**——dockview 所有枚举接口（`api.panels` / `groups` / `toJSON`）**只回
  已实例化的**。`DockviewOptions` 六十多个字段里没有 `catalog` / `availablePanels` 这类
  东西
- **身份与元数据**——`title` 在它那儿是 `addPanel` 的入参、不是可查询的目录项；
  `icon` / `client` / `entryId` / `pkg` 它完全没有

一句话：**dockview 管「已经决定要有这个窗格之后它长什么样」，`pane-registry` 管「有哪些窗格
值得存在」**——后者 dockview 从设计上就留给宿主。

## 注册时检查什么

注册表本体的四条判据，都写进了测试：

1. **一条条目一个命名空间**——键是 `entryId` + 窗格 id。同一个包的两条条目各注册一个
   同名的窗格，两条都在，这不叫重名
2. **重名时后注册的生效，但要告警**——跟命令总线一个规矩，一个仓里两套重名规则是无谓的
   记忆负担
3. **空 id / 空 title 抛错**，不是静默忽略——重名是「两条都说得清，该听谁」，而空 id
   是「这个窗格根本没说自己是谁」。让它登记进表只会在容器里多出一个点不开的空白，而且回头
   查不到源头。注册参数是插件自己写死的常量，抛在它自己的 `apply` 里、日志写明是谁，
   好查得多
4. **`client` / `style` 给了就必须是 `file://` 地址，否则抛错**：`client` 的路径以 `.js` 结尾，`style` 的路径以
   `.css` 结尾（看的是地址的路径部分，后面带查询串不影响），都从插件自己的模块地址算，如
   `new URL('./client.js', import.meta.url).href`。报错写明哪个包、哪个窗格、哪个字段、收到的值和该给什么，
   外壳不替插件改地址。两个都可以不给：不给 `style` 就不注入样式表；不给 `client` 的窗格照常登记，打开后
   窗格里显示一句报错。检查放在注册这一步，是因为每个插件的窗格都要经过它，理由见轨迹卡
   [窗格地址在注册时检查](/trajectory/2026-09-24-pane-address-check-at-register)
