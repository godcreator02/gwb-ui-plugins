# 样式与组件

工作台上带界面的插件有好几个：外壳自己占整页，其余的各自渲染一个窗格。它们的界面**全都渲染在同一个
页面上**，而且是**分别构建、分别发版、装进同一个 home 运行时才第一次放在一起**的。

这一页讲的就是这件事怎么成立：什么东西全页共享一份、什么东西必须各一份且互相隔离、
共享的到底是源码还是运行时的对象。「样式隔离为什么用 Tailwind 类名前缀、不用选择器限定范围（scope）」的
判据在[隔离靠名字，不靠位置](#隔离靠名字不靠位置)，否决的候选在[第五节](#五取舍与结论)，具体遇到的问题记在
[遇到过的问题](/docs/walls)。这一页讲的是原理：为什么非得这么分，以及一次启动从注入第一张样式表到
插件在容器里渲染出第一个像素，中间每一步为什么排在那个位置。

## 一、一张页面，三种共享

### 先看物理事实

不管这套东西设计成什么样，浏览器给的条件是固定的，一共三条：

- **只有一个 DOM。** 每个插件画出来的元素，跟别人的元素是同一棵树上的兄弟或后代
- **只有一套级联。** 页面上所有 CSS 规则最终排进同一个优先级体系里比大小，不存在
  「这条规则只在这一块里参与比较」这种东西（除非使用 Shadow DOM——不采用它的理由在第五节）
- **只有一个 JS realm。** 一个全局对象、一份模块缓存、一份 importmap

「多个插件共享一套外观」这句话听着是一件事，对照这三条物理事实其实是**三个不同的问题**，
答案也各不相同：

| 问的是什么 | 答案 | 凭什么 |
| --- | --- | --- |
| 颜色、圆角、字体这些**值** | **全页共享一份** | CSS 自定义属性沿 DOM 继承，`:root` 上写一次全树读得到 |
| 工具类这些**规则** | **各一份，而且必须互相隔离** | 每个插件按需编译，各是各的子集，放在一起会互相覆盖 |
| 按钮、菜单这些**组件** | **共享的是源码的出处，不是运行时的对象** | 每个插件各自拉取源码、各自打包 |

下面三节各讲一个。

### 第一问：值——全页共享一份

这一问浏览器本身就解决了。CSS 自定义属性（`--background` 这种）**沿 DOM 继承**：在 `:root`
上写一次，整棵树上任何一个元素读 `var(--background)` 都读得到，不管这个元素是谁画的、
什么时候插进来的。

所以外壳里那张令牌表只做一件事：把语义变量的值在页面上写一份。亮色写在 `:root`、暗色写在 `.dark`
（`<html>` 上的一个类）：

{/* ref file="../plugins/shell/src/tokens/tokens.css" lines="1-1" hash="e19065a8a9f5" blob="ce74d1a59f41" */}

**换主题＝换这一份值。** 插件那边的规则里写的是 `var(--primary)` 而不是某个具体颜色，所以
页面上这份值一变，所有插件立即跟着变，**一个都不用重新构建**。状态栏的亮暗开关做的事就是
给 `<html>` 加一个类名而已。

同一份表还负责两件全页只该有一份的事——给所有元素一个默认边框色、给 `body` 定底色与字体：

{/* ref file="../plugins/shell/src/tokens/tokens.css" lines="98-111" hash="82e9d70b2db6" blob="ce74d1a59f41" */}

字体那一行尤其要紧：**不经 Tailwind 工具类的那些 DOM**（dockview 渲染的标签条、插件里没写工具类的
普通 HTML）全靠从 `body` 继承。

表里几个取值各有理由：

- **整个工作台一种字体：更纱黑体等宽（Sarasa Mono SC）**，正文与代码同一个字体族。中日韩文字与拉丁字母
  在同一套字形里，中英混排的字重、基线、字宽都对得齐，不靠系统回退去挑一个不受控的中文字体；机器上
  没装它时按后面的字体栈回退。正文与等宽仍是两个变量（`--gwb-font-sans` / `--gwb-font-mono`）：插件写
  `font-mono` 表达的是「这里是代码」，将来给代码换字体只改一处；主题插件的字体覆盖写的也是这两个名字
- **字号沿用 Tailwind 通行的刻度，行高按中文放宽**：方块字在拉丁文字的紧行高下显得挤，正文 1.65、
  小字 1.5；标题反过来越大行高越小，不然大标题的行与行之间会散
- **暗色底不用纯黑**：页面底色与卡片底色分两级，卡片更亮——纯黑底上没有东西能显得浮起来
- **Tailwind 出厂的刻度（间距、字重、阴影、过渡、容器断点）也写在这张表里**：前缀会改写出厂变量名，
  页面上没人声明改写后的名字，插件产物里就会留下 `var(--前缀-spacing, 0.25rem)` 这种带字面默认值的引用。
  值写进令牌表、映射文件接管这些键之后，产物里不再有字面默认值，这些尺寸也能随主题换；值照抄 Tailwind
  4.3.3 的出厂默认，观感不变

### 第二问：规则——各一份，而且必须互相隔离

这一问才是这整页的核心，而且它的必要性**不是显然的**——很容易觉得「大家用的都是同一套
Tailwind，表合并成一张不就行了」。不行。得一步一步看清楚为什么。

**第一步：Tailwind 是按需编译的。** 它扫描源码，你用到哪个类就编译哪条规则，没用到的一个
字节都不输出。所以每个插件那张表都是**全集的一个子集，而且各是各的子集**——甲插件用到的那些，
乙插件多半没用到；乙插件用到的那些，甲插件也未必有。

**第二步：子集本身没问题，问题出在几张子集表放进了同一个层（layer）。** Tailwind 的工具类全在
`@layer utilities` 里，插件的表只写这一层、不声明层与层的顺序：

{/* ref file="../plugins/baseui/src/client/styles.css" lines="6-10" hash="33bd996daefc" blob="58e7b2609682" */}

顺序由**先加载的那张令牌表**声明，而这张表还得把 preflight 包进 `base` 层——CSS 里
**未分层的规则优先级高于所有分层规则**，preflight 原样放进去就是一份未分层的规则，会覆盖每一个
插件的工具类：

{/* ref file="../plugins/shell/build.ts" lines="140-157" hash="5d0202b6fd31" blob="4dc419913506" */}

**第三步：同层、同权重，谁生效只看文档顺序。** 于是问题是这样发生的——甲插件的元素上
带着两个类，一条管四边、一条只改左右；乙插件只用到了前者，所以**乙的表里没有后者**；而乙的表
**后加载**。层里的顺序就成了「甲的①、甲的②、乙的①」，乙那条①排在甲的②后面，**把甲的元素
整个重置回①的样子**。

**而且没有任何一处报错**：两张表都编得对、都加载成功了，只是互相覆盖了。构建通过了，控制台
是干净的，页面上只有「这块怎么跟我写的不一样」。

这个过程按时间先后发生，写成文字必然是一串「先……然后……于是……」，所以做成了动画：

**所以隔离是必需的，不是过度讲究。** 要选的只是**隔离的手段**。

### 隔离靠名字，不靠位置

隔离两张表，直觉上的办法是**按位置**：把甲插件那张表里的每条选择器都改写成「只有位于甲插件那个
容器底下的元素才算」。本仓不采用这个办法。不采用的理由不是它不管用，是它的**失效点在
运行时**：

- 弹出层默认 portal 到 `<body>` 上，一移到 `<body>` 下就不在那个容器底下了，整个菜单一个类名都不生效
- 外壳的根是每个窗格的祖先，所以外壳那张表的规则对所有窗格里同名的元素照样成立
- 哪张表先注入页面决定谁覆盖谁，而那个顺序是运行时才定的

三种都不报错。**DOM 的位置是运行时才确定的**，所以按位置隔离，等于让隔离依赖一堆隐含前提，
前提破了没有任何人会告诉你。

本仓采用的是**按名字**隔离：让类名从源头就唯一（每个插件一个短前缀，类名写成 `baseui:flex` /
`shell:flex` 这种）。规则仍然全页有效、跟 DOM 祖先关系无关，但**它只可能匹配到本插件渲染出来的
元素**——因为别的插件根本不会写出这个名字。

按名字隔离，失效点就不在运行时，而在写代码那一刻：

| | 按位置隔离 | 按名字隔离 |
| --- | --- | --- |
| 靠什么隔离 | DOM 祖先关系 | 类名的唯一性 |
| 弹出层 portal 出去 | 整层没有样式 | 无关，照样有样式 |
| 加载顺序 | 是隐含前提 | 不参与 |
| 会怎么坏 | 三种，全部静默 | 只剩一种：忘写前缀 |
| 什么时候看得见 | 某个弹层被打开、某两个插件同时装上的那天 | **当场**——那个类不生效，写的人打开页面就看见 |

<Diagram name="name-isolation" title="按位置隔离与按名字隔离：portal 出去的菜单有没有样式">

- 按位置隔离：规则写成 `[data-gwb-plugin="baseui"] .px-2`，只匹配那个窗格容器底下的元素；窗格里的按钮匹配得上，portal 到 body 下的下拉菜单匹配不上，整层没有样式，也不报错
- 按名字隔离：类名写成 `baseui:px-2`，编出的规则 `.baseui\:px-2` 全页有效；按钮和 portal 出去的菜单都匹配得上，别的插件不会写出这个类名

</Diagram>

「忘写前缀」还能由 devkit 的样式检查拦住（第四节），而上面那三种一条都拦不住。

**工具链原生支持这个做法**，不用自己改写：Tailwind 4 的 `prefix()` 写在拆开的主题导入上、
shadcn 的 `components.json` 里有 `tailwind.prefix`、`cn` 那个包（tailwind-merge）对带前缀的
类名本来就合并得对。按位置隔离则要自己写 postcss 改写，外加给每个带弹出层的组件打补丁
——两份要自己维护的成本，得到的隔离还更弱。

### 第三问：组件——共享的是源头，不是运行时

按钮、下拉菜单这些东西，两个插件长得一模一样，靠的**不是**它们运行同一段代码。

每个插件自己有一份 `components.json`，要什么组件就从 shadcn 官方拉什么，**拉下来就是这个插件
自己目录里的一个 tsx 文件**，跟着这个插件一起被 esbuild 打包进它自己的产物：

{/* ref file="../plugins/baseui/components.json" lines="6-12" hash="c71e1f15e2f1" blob="7a64d0da68a9" */}

那两个插件的按钮长得一样，是因为**源码来自同一处**（同一个 registry、同一个 `style` 与
`baseColor`），而颜色**读的是同一份令牌**。运行时它们是两段互不相识的代码。

这么做的代价是每个插件的打包产物里各有一份按钮的字节。得到的是：一个插件想改自己那个按钮，
改自己目录里那个文件就行，**不用发一个共享包、不用等别人升级、也不可能改坏别人的**。
「共享一个组件库」这条候选被否决的实测理由在第五节。

`prefix` 那一行让 CLI 直接写出带前缀的类名，所以拉下来的组件不用手改。按名字隔离也不要求弹出层
留在窗格容器里，所以拉下来的组件**就用官方原版**，不用逐个打补丁。

### 还有一份东西要共享：React 实例

JS 的模块解析由 kernel 提供，React 的版本和文件归 shell。shell 构建四个 ESM 文件，用 browserImports() 返回地址，在 setShell 前经 registerImports 登记。页面 await prepareImports 后才 import shell；窗格也在 import 前准备映射。

{/* ref file="../plugins/shell/src/browser-imports.ts" hash="b3a836f060d8" blob="981722f5237b" */}

构建从 @godcreator/gwb-shell/browser-imports 取 Object.keys(browserImports()) 作为 external。其他提供方也可以用相同代码契约登记模块；没有提供方的库打包进本插件。

<Diagram name="importmap-flow" title="React 的代码提供方与页面准备">
- shell 构建 React，browserImports() 给出本地文件 URL
- 主进程登记，页面 prepareImports 追加 importmap
- 准备完成后动态加载，所有使用方解析到相同 URL
</Diagram>

**这份共享现在换来的是什么，要说清楚**：一是字节——带界面的每个插件不必各带一份 React；二是
**为将来留的余地**。眼下的窗格契约交给插件的是一个 DOM 容器加一个挂载函数，插件在容器里自己 `createRoot`，
**没有任何 React 对象跨插件传递**，所以「同一份实例」这件事今天并不是正确性的前提。但如果哪天
契约变成「插件交出一个 React 组件、由外壳来渲染」，那时它就是必要前提了——两份 React 实例下
hook 立即报错。现在把这条留着，比将来再统一便宜得多。

### 从头到尾的启动顺序

把上面几件事按时间排一遍，就是外壳启动时做的事。每一步都有它必须在那个位置的理由：

**第一步：shell 登记运行时，然后页面准备 importmap，再 import 外壳的浏览器代码。** 提供方先登记，页面等待 prepareImports 成功，才解析模块。

{/* ref file="../plugins/shell/src/client/index.tsx" lines="667-671" hash="ef6825436662" blob="2bf1b309827d" */}

**第二步：外壳问一次 `shell.env`**，拿到 home、三张样式表的地址，外加这一刻的用户外观样式
（第四步用）。地址由 node 端算（自身的表从 `import.meta.url` 算，令牌表经 `fileUrlOfPackageExport` 按包名解析到本包自己的产物），**顺序是写死的**：
令牌、dockview、外壳自己那张。

{/* ref file="../plugins/shell/src/index.ts" lines="28-41" hash="4e6fc7ac5d7c" blob="d8029385df74" */}

{/* ref file="../plugins/shell/src/index.ts" lines="208-226" hash="7e8c67575845" blob="d8029385df74" */}

**第三步：三张表全部注入、并且都等到加载完成，才往下走。** 有一张加载不了，外壳就不往下走，根节点上写一句
「外壳起不来」和那张表的地址。令牌那张必须最先——层顺序是它声明的；
dockview 那张表的类名不由我们写（改不了名，也就加不上前缀），所以它整张不做隔离；
外壳自己那张类名一律带自己的前缀。

**第四步：把主题插件的启动样式注入在这三张之后。** 值是第二步 `shell.env` 带来的——node 端处理
`shell.env` 时去取（装了主题插件才取，见第三节那条可选命令），浏览器端只负责插入页面。
用户自己写的那段 CSS 要能覆盖令牌的默认值，同权重下靠文档顺序决定谁生效，所以它得是 head 里靠后的那张；
而「重启后启动即生效」要求它在第一帧之前插入页面。

{/* ref file="../plugins/shell/src/client/theme-boot.ts" lines="6-18" hash="1826a6969b08" blob="20e3479e96b1" */}

**第五步：加上 `.dark`、加上身份标记，然后 `createRoot`。** 深色是默认状态，令牌的暗色那一套在这里
生效。身份标记只用来辨认，不参与任何选择器（第四节「窗格容器上那两样东西」还会再说一遍）。

{/* ref file="../plugins/shell/src/client/index.tsx" lines="623-629" hash="7a270f2fe89c" blob="56f920646dec" */}

**第六步：开一个窗格时**——从注册表里取这个插件注册时提供的两个地址 → **先注入它的样式表、等它加载完成**
→ 准备 importmap → 再动态 import 它的脚本 → 调它的挂载函数、把容器交出去 → 保存它返回的清理句柄。样式表加载不了就停在这一步，
窗格里显示「加载失败」和那张表的地址，不带着没样式的界面继续挂载。

{/* ref file="../plugins/shell/src/client/PluginPane.tsx" lines="119-154" hash="4adceb25a3d2" blob="056b20dadf53" */}

最后一步里「等它加载完成再 import」不是讲究，是必需的：`<link>` 是异步取的，插件的第一帧完全可能
发生在样式表加载完成之前，那一瞬间是一堆没有样式的元素。这两件事因此放在同一个清理单元里——拆成两处
就只剩「谁先执行」这种靠排列顺序的隐含约定。

## 二、模块划分与依赖方向

五个模块，依赖**全是单向的**：

| 模块 | 管什么 | 它**不知道**什么 |
| --- | --- | --- |
| 令牌表（在外壳包里） | 值：语义变量的两套值、preflight、层顺序声明 | 不知道有哪些插件，不知道 Tailwind 前缀这回事，没有 node 端（产物是两份 css，2026-09-22 起随外壳包发布） |
| 每个插件自己的表 | 规则：本插件用到的那些工具类，类名带本插件的前缀 | 不知道别的插件存在，不知道值最终是多少（它只写 `var(…)`） |
| 外壳 | 转交与容器：注入三张表、给每个窗格一个容器、把这个窗格变成容器查询的根 | **不知道任何插件的类名**，也不知道插件的表里有什么 |
| 主题插件 | 用户覆盖：字体两项 + 一整段自定义 CSS，交给外壳在最后注入；「外观」窗格预览时直接改外壳注入的那张样式元素 `#gwb-theme-style` | 不知道任何插件存在，也不知道外壳把它注入在第几位（node 侧只交出一段字符串）；只认得那张样式元素的 id，这个 id 与外壳各写一份，见[插件之间怎么连](/docs/wiring) |
| 内核 | 提供模块登记和页面准备机制；React 归 shell | 不认识任何类名，不认识任何插件 |

<Diagram name="module-deps" title="本仓各模块的依赖方向">

- 带界面的插件依赖令牌表（构建期引用映射文件、运行期读页面上的变量值）与外壳（注册窗格时交出两个地址，浏览器侧 `import type` 外壳的类型）
- 外壳经一条可选命令 `theme.startupCss` 用到主题插件，没装主题插件外壳照常运行
- 本仓的插件以 peer 依赖基础仓插件（commands、data、settings、logger 等），基础仓不依赖本仓
- shell 提供 React，内核接收通用映射，不依赖具体插件

</Diagram>

依赖方向是：**插件 → 令牌**（构建期引用映射文件 `theme.reference.css`、运行期读页面上那份变量值），**插件 → 外壳**
（注册窗格时提供自己那两个地址），**外壳 → 主题插件**（一条可选命令，外壳没有它也照常运行），**内核 → 谁都不依赖**
（只提供通用登记与准备机制）。反向的箭头一条都没有：

- 令牌表不知道有哪些插件，所以加一个插件、删一个插件，它一个字都不用改
- 外壳不知道插件的类名，所以插件改自己的样式，外壳不用重新构建
- 主题插件不知道谁在用它的启动样式，外壳没装它就没有这一步，它自己照常运行

**换掉实现要不要改调用方**，逐个检查都不用改：令牌把 zinc 换成别的底色，插件一行不改；
一个插件把自己的表从头重写，外壳一行不改；主题插件被另一个插件替换（只要还响应那条命令名），
外壳一行不改。

## 三、接口划分

这一层是**契约**：变了就得所有人跟着变，所以要一条条引用源码写明。

### 令牌的契约是两个文件，缺一不可

**变量值文件**（`tokens.css`，页面加载的那张）交出去的是一份**变量名清单**——`--background` / `--primary`
这些名字。这份清单**只加不删**：删掉一个名字，所有插件的表里那条 `var()` 立即读到空值，而读到空值是
静默的。

**映射文件**（`theme.reference.css`）是插件在构建期引用的那份，它把「类名怎么解析到变量」这件事告诉编译器，但**一个变量
声明都不输出**：

{/* ref file="../plugins/shell/src/tokens/theme.reference.css" hash="943b2ea0f02b" blob="f5bcf4c3f472" */}

值和映射**必须分成两个文件**，理由见下一节。插件那边引用的写法是固定的一行，
第六节有可以照抄的出处。

<Diagram name="token-flow" title="颜色令牌在构建时与运行时各经过哪几处">

- 构建时：外壳的 `theme.reference.css` 用 `@theme inline` 把颜色名映射到令牌变量（`--color-primary: var(--primary)`），不输出任何变量值
- 插件的样式入口引入这个映射文件、写 `prefix(baseui)`，编出的类是 `.baseui\:bg-primary`，规则里只有 `var(--primary)`
- 运行时：外壳最先注入令牌表 `tokens.css`，亮色值写在 `:root`、暗色值写在 `.dark`
- 插件元素上的 `baseui:bg-primary` 读 `var(--primary)`，沿 DOM 继承读到页面上那一份值；状态栏切换 `<html>` 上的 `dark` 类，所有插件一起变

### 这两个插件各依赖谁

主题插件与基础界面插件各注入了哪些服务、哪些是必需依赖哪些是局部注入、按名字调用了别家哪些命令，
见[插件之间怎么连](/docs/wiring)。依赖都不反向：没装主题插件的 home 里，外壳只是少一份启动样式（上一节那条
可选命令）；没装 logger / plugin-manager 的 home 里，基础界面插件只是少注册那个窗格。

**为什么日志与插件管理的界面合在基础界面一个插件里**（2026-09-12 三仓拆分时决定）：logger 与
plugin-manager 是只有 node 端的 core 插件，各自的浏览器端代码不各发一个包，而是统一放进
基础界面——每个小包单独发版、写文档、维护 peer 的开销合并到一个发布单元上，共享组件（shadcn 那套）
也只有一份。做法参照 VS Code 的内置视图：**合并的是发布，不是开发**——`panes/` 下的窗格之间互不
import，只 import `components/` 下的共享组件。

### 其他浏览器模块提供方

其他插件可以用代码出口与 registerImports 提供模块。使用方写明 peer 依赖并从提供方取外置名单；未声明提供方的库打包进自己的 client.js。同名不同 URL 拒绝，已加载地址变化需整页重载。

## 四、关键代码

下面这几段是「看了就懂这个机制为什么长这样」的那种，每段配一句它说明了什么。

### 层顺序与 preflight，为什么由令牌表来管

{/* ref file="../plugins/shell/build.ts" lines="140-157" hash="5d0202b6fd31" blob="4dc419913506" */}

**这段说明什么**：插件的表只写工具类那一层、不声明层与层的先后，所以顺序只能由**先加载的那张**
来声明。而 preflight 是一份未分层的规则，**未分层的规则优先级高于所有分层规则**——不把它包进
`base` 层，它会覆盖每一个插件的工具类。**「未分层的规则优先级高于所有分层规则」这一条语法事实，
在这一页解释了两件事**：preflight 为什么必须包起来，以及（下面会讲到）用户自己那段
自定义 CSS 为什么能覆盖一切。

### `theme.reference.css` 为什么单独一个文件

{/* ref file="../plugins/shell/src/tokens/theme.reference.css" lines="1-2" hash="c42f2e242752" blob="f5bcf4c3f472" */}

**这段说明什么**：以引用的方式导入只能阻止主题块输出，**阻止不了普通规则输出**。把带
`:root { … }` 的变量值文件（`tokens.css`）一起引进插件的构建里，每个插件的表里都会多出一整份 `:root`，和页面上那张
重叠成两份来源。拆开之后，映射让类名解析得出来，而值仍在运行时取页面那张表的变量——
主题一致性不丢。

这个做法有一条**限制**，出在插件样式入口导入 Tailwind 内置主题时带的那个前缀上：

{/* ref file="../plugins/baseui/src/client/styles.css" lines="6-6" hash="774f8f302acb" blob="58e7b2609682" */}

前缀会把 Tailwind **内置的**主题变量名也改掉（每个插件的前缀不同，名字对不上），所以指望在
页面上全局声明一份 Tailwind 默认主题变量去影响所有插件是行不通的。**语义令牌只能经映射文件
传入值**——这不是多余的一层，是唯一可行的做法。

### 插件的样式入口：五行，一行都不能省

{/* ref file="../plugins/baseui/src/client/styles.css" lines="6-10" hash="33bd996daefc" blob="58e7b2609682" */}

**这段说明什么**：第一行把内置主题引进来**只为让类名解析得出来**，一个变量声明都不输出，
前缀写在这条拆开的导入上才生效；第二行是令牌的映射文件，**不引它颜色类整个是空的**；
第三行只引工具类、不引 preflight（那是页面级的一份），并关掉自动扫描、由最后那条指定扫描
范围——不关的话 `dist/` 里的产物也会被扫进来，凭空多出一批没人用的类，也不报错；第四行给的是动画
那一类类名，**不引就一个字节都不输出**，它顺带输出的一批不带前缀的全局 `@keyframes` 与 `@property`
每张表各一份、内容相同，无害。四条 import 全是「不引就静默为空」，所以文件头的注释写明一行都不能省。

### 注入样式表：等它加载完成，而且永不移除

{/* ref file="../plugins/shell/src/client/asset.ts" hash="a516d6664273" blob="875b98ab0c68" */}

**这段说明什么**：整个文件就两件事。**等 `load` 事件**——只 append 是不够的，第一帧完全可能
发生在样式表加载完成之前。**注入过就不移除**——移除它需要引用计数，而计数错了的症状是「关掉一个窗格，另一个窗格
的样式跟着没了」，静默，且要两个窗格同开才复现；留着的代价只是内存里一份 CSSOM。

### 窗格容器上那两样东西

**这段说明什么**：`@container` 让这个窗格成为**容器查询的根**——插件里写的 `@sm:` / `@md:`
这类变体问的是**这个窗格现在有多宽**，跟整窗大小无关。窗格里这份界面跟着这个窗格的宽度走：
工具条窄了折行、宽了收回一行（要按宽度换向的排布，用的就是 `@md:` 那类变体），

旁边那个身份属性**只用来辨认**。按位置隔离的方案要靠它限定选择器范围；本仓按类名前缀隔离，
加不加它样式都一样。留着是为了在 devtools 里一眼看出这个窗格是哪个插件的。**正因为少加一个也
不会有任何现象**，别把它当成「样式生效的前提」去写代码。

### 怎么检查「忘写前缀」：devkit 的样式检查

前缀方案唯一的失效点是忘写前缀，而它**当场就看得见**——但看得见不等于拦得住。拦它的不是本仓的测试，
是 devkit 的样式检查：`devkit.dev` 构建之后、`devkit.release` 发版之前，对构建后有 `dist/style.css` 的插件都跑一遍，
没过的 `devkit.dev` 不装进 home、`devkit.release` 一个包都不发。检查只有 devkit 里一份（生命周期插件仓
`gwb-lifecycle-plugins` 的 `plugins/devkit/src/style-check.ts`），本仓不留副本。它查两层：

**源码层**：把样式入口所在目录下 `.tsx` 里的字符串字面量切成 token，拿插件自己那份样式入口**去掉前缀**当输入，
逐个交给 Tailwind 编译器，看「这个 token 编得出规则吗」。**去掉前缀是关键**：带前缀的编译器对一个漏了前缀的
类只会返回「不认识」，跟对任何一句中文的回答一模一样，分不出漏没漏；去掉之后，「编得出来」
本身就等价于「它是个类名」。编译是**增量**的——候选一旦交给它就留在里面，所以判据不是「跟空基线比」，
而是**逐个传入，看这一步的输出有没有变**。同一层还查前缀排在变体后面（`hover:baseui:…`，Tailwind 不报错、
一条规则都不出）的写法。

**产物层**：`dist/style.css` 里的类选择器一律带本插件的前缀（唯一放行的是页面级的亮暗标志 `.dark`，它只以
**祖先**的身份出现）；身份属性 `data-gwb-plugin` **出现就算失败**——有它就说明构建用的是
按位置隔离，而症状（弹出层没有样式）得把菜单打开才看得见，构建照样通过；另外查 `var()` 不写死 fallback、
颜色类只用外壳 `theme.reference.css` 与本插件样式入口里声明的色名。

这套检查有两处看不到：它只扫 `.tsx`，`.ts` 文件与模板串 `${…}` 插值里拼出来的类名不查；反过来，`.tsx` 里任何
字符串只要跟工具类同名就会被当成漏了前缀的类名，所以不是类名的字符串（比如外观窗格里与 `font-sans` 同名的设置键）
放在 `.ts` 文件里。

### 样式检查查不出的那一条：标记类

{/* ref file="../plugins/baseui/src/client/panes/logger/index.tsx" lines="325-328" hash="5b044d463983" blob="a70e8f4051de" */}

## 五、取舍与结论

这一节写两样：**否决的候选**与**残余的耦合**。

### 否决的三个候选

**Shadow DOM。** 最彻底的隔离，每个插件一个 shadow root，样式天然出不去也进不来。否决的理由有两条：
一是 `@property` 声明在 shadow root 里被忽略，而 Tailwind 4 的内部机制大量用它；二是弹层
组件的「点外面关掉」那类判断在 shadow 边界上有一堆历史问题。**为了一层隔离，牺牲组件生态的
可用性，不划算**——何况值本来就该穿透，shadow 恰恰把值也挡在外面。

**共享一个组件库。** 所有插件从一个包里 import 按钮。基础插件仓（gwb-base-plugins）实测过：**CSS 一点都没省下**——因为每个插件
仍然要为自己用到的类编一张表，共享的只是 JS 那点字节；换来的是一条必需依赖，那个包升一次版
所有插件都得跟着升级。

**每个插件全自带。** 连令牌也各带各的。那样**主题的一致性无从保证**：几个插件几份颜色值，
换主题要所有插件一起重新构建、一起发版。这条恰恰是「值必须全页共享一份」那一问的反证。

### 否决的是共享运行时，共享源码的途径保留

「共享一个组件库」否决的是**运行时**——所有插件从同一个包 import。但「生态将来要不要
自己的组件源头」这个可能没有跟着排除：shadcn 的 registry 本身是**可自建的开放协议**，
官方那份只是它的第一个实现。

- **协议同构。** 自建与官方是同一份 `registry.json` schema，消费端是同一个 `shadcn add`
  （按 URL，或登记进 `components.json` 的命名空间）。gwb 一直在用同样的关系：
  官方 npm 源与本机 Verdaccio，就是同一协议的两个实现。
- **前缀改写是协议自带的。** registry 里的组件源码一律无前缀，CLI 拉取时按**消费者自己**
  `components.json` 里的前缀改写类名——跟今天从官方拉组件是同一个动作：

{/* ref file="../plugins/baseui/components.json" lines="11-11" hash="f6a0951479f4" blob="7a64d0da68a9" */}

  所以同一份源码拉进任何插件都自动带上那个插件的前缀，值照旧读令牌表。**现有的这些规矩
  已经允许将来增加或更换组件源头，启用时不用改架构。**
- **版本管理要自己做。** registry 是一份静态清单：无版本语义、没有 lockfile，不固定引用
  就是浮动依赖——要可复现，固定到 tag 或完整 commit SHA。而且拉下来就是消费者自己的代码，源头修了
  bug 不会自动到达，各插件要各自重拉。
- **什么时候值得建，只看一条**：同一个组件在两个插件里各复制了一份、并且开始各自漂移的那天，才
  值得建。在那之前，官方源头 + 各插件各自拉取已覆盖全部需求——插件作者不需要为「组件怎么共享」
  操心任何事。

### 残余的耦合，一条

**Tailwind 内部那批 `@property` 不随前缀走。** 每张表各注册一遍同名的那批，同名的以后注册的
为准。所以**全生态仍然得同一个 Tailwind 主版本**——这条不是前缀方案引入的，但前缀方案也没消掉
它。

还有一条明显的代价：**源码里每个类多一个前缀**，一直要付。

## 六、写一个带界面的插件

原理讲完了，做法就很短。

**一、`components.json` 填两处**：`tailwind.css` 指一个真实存在的样式入口路径（这个字段是
必填的，省略的话会报一句没有细节的错），`tailwind.prefix` 填本插件的短名——CLI 拉下来的组件因此自带
前缀，一处都不用手改。形状照第一节引用的那份抄。

**二、写那五行样式入口。** 照第四节引用的那五行原样抄，只把前缀换成本插件的短名。四条 import
一条都不能省。

**三、构建脚本补一步**：编译本插件那张表，输入就是那份入口，扫描范围由入口里最后那条决定。

**四、拉组件**：`shadcn add` 什么就有什么，拉下来是本插件目录里的文件，跟着本插件一起打包。
组件的运行时依赖**打包进本插件的产物**，别外置（不在 importmap 里的裸名，外置就会在运行时报错）。

**五、注册窗格时把两个地址提供给外壳**，值从自己的 `import.meta.url` 算成 `file://`。

**六、用 `devkit.dev` 装进隔离 home**：它构建之后跑第四节那套样式检查，回执 `ok: true` 才算过；不用在插件里另抄检查前缀的测试。

### 会静默失效的几种写法

这一类有个共同的性质：**「编不出规则」在编译器眼里跟「这不是个类名」是同一回事**，
所以它们全都不报错。

| 干了什么 | 现象 | 怎么防 |
| --- | --- | --- |
| 入口里没引令牌的映射文件（`theme.reference.css`） | 颜色类**整个是空的**——语义色编不出对应的变量引用 | 五行入口一行不省 |
| 入口里没引动画那个包 | 动画那一类类名一个字节都不输出，菜单打开关闭没有过渡动画 | 同上 |
| 类名忘了带前缀 | 那个类不生效，页面上就是那一处没样式 | devkit 的样式检查（只查 `.tsx` 里的字面量） |
| 标记类（当锚的那种）没带前缀 | 变体的选择器**永远不命中**，类名和规则都在，只是对不上 | **样式检查查不出来**，只能靠知道这条 |
| 在插件的表里写 `:root { --primary: … }` | 要么覆盖了全页，要么跟别处不一致 | 令牌是页面共享的那一份，插件的表里不碰它 |
| 想按窗格宽度换布局，却写成了视口断点 | 按整窗大小判，拖窄这个窗格毫无反应 | 用容器查询变体（带 `@` 的那种），根是外壳给的容器 |

最后一条值得多说一句：**窗格不是视口**。工作台上一个插件可能被拖成 300px 宽的一条，也可能占
满 1000 多像素，而整窗大小自始至终没变过。插件里的响应式判据要问的是「我这个窗格现在有多宽」，
不是「这个窗口有多大」。
