# 样式与组件

这条线上带界面的插件有好几个：外壳自己占整页，其余的各画各的一个窗格。它们的界面**全落在同一张
页面上**，而且是**分别构建、分别发版、装机时才第一次见面**的。

这一页讲的就是这件事怎么成立：什么东西全页共享一份、什么东西必须各一份且互相隔离、
共享的到底是源码还是运行时的对象。**方向上的决定本身不在这里**——「样式隔离为什么从选择器 scope 换成
Tailwind 前缀」记在[定过的事](/docs/decisions)的 2026-09-09 那条，遇到过的问题记在
[撞过的墙](/docs/walls)。这一页讲的是原理：为什么非得这么分，以及一次启动从注入第一张样式表到
插件在容器里画出第一个像素，中间每一步为什么排在那个位置。

---

## 一、一张页面，三种共享

### 先看物理事实

不管这套东西设计成什么样，浏览器给的条件是固定的，一共三条：

- **只有一个 DOM。** 每个插件画出来的元素，跟别人的元素是同一棵树上的兄弟或后代
- **只有一套级联。** 页面上所有 CSS 规则最终排进同一个优先级体系里比大小，不存在
  「这条规则只在这一块里参与比较」这种东西（除非上 Shadow DOM——那条路否掉的理由在第五节）
- **只有一个 JS realm。** 一个全局对象、一份模块缓存、一份 importmap

「多个插件共享一套外观」这句话听着是一件事，落到这三条物理事实上其实是**三个不同的问题**，
答案也各不相同：

| 问的是什么 | 答案 | 凭什么 |
| --- | --- | --- |
| 颜色、圆角、字体这些**值** | **全页共享一份** | CSS 自定义属性沿 DOM 继承，`:root` 上写一次全树读得到 |
| 工具类这些**规则** | **各一份，而且必须互相隔离** | 每个插件按需编译，各是各的子集，叠在一起会互相污染 |
| 按钮、菜单这些**组件** | **共享的是源码的出处，不是运行时的对象** | 每个插件各自拉取源码、各自打包 |

下面三节各讲一个。

### 第一问：值——全页共享一份

这一问浏览器本身就解决了。CSS 自定义属性（`--background` 这种）**沿 DOM 继承**：在 `:root`
上写一次，整棵树上任何一个元素读 `var(--background)` 都读得到，不管这个元素是谁画的、
什么时候插进来的。

所以外壳里那张令牌表只做一件事：把语义变量的值在页面上写一份。亮色写在 `:root`、暗色写在 `.dark`
（`<html>` 上的一个类）：

{/* ref file="../plugins/shell/src/tokens/tokens.css" lines="1-9" */}

**换主题＝换这一份值。** 插件那边的规则里写的是 `var(--primary)` 而不是某个具体颜色，所以
页面上这份值一变，所有插件立即跟着变，**一个都不用重新构建**。状态栏的亮暗开关做的事就是
给 `<html>` 加一个类名而已。

同一份表还负责两件全页只该有一份的事——给所有元素一个默认边框色、给 `body` 定底色与字体：

{/* ref file="../plugins/shell/src/tokens/tokens.css" lines="99-112" */}

字体那一行尤其要紧：**不经 Tailwind 工具类的那些 DOM**（dockview 画的标签条、插件里的裸
HTML）全靠从 `body` 继承。

### 第二问：规则——各一份，而且必须互相隔离

这一问才是这整页的核心，而且它的必要性**不是显然的**——很容易觉得「大家用的都是同一套
Tailwind，表合成一张不就完了」。不能。得一步一步看清楚为什么。

**第一步：Tailwind 是按需编译的。** 它扫源码，你用到哪个类就编哪条规则，编不出来的一个
字节都不出。所以每个插件那张表都是**全集的一个子集，而且各是各的子集**——甲插件用到的那些，
乙插件多半没用到；乙插件用到的那些，甲插件也未必有。

**第二步：子集本身没问题，问题出在几张子集表叠进同一层。** Tailwind 的工具类全在
`@layer utilities` 里，插件的表只写这一层、不声明层与层的顺序：

{/* ref file="../plugins/baseui/src/client/styles.css" lines="31-35" */}

顺序由**先加载的那张令牌表**声明，而这张表还得把 preflight 包进 `base` 层——CSS 里
**未分层的规则优先级高于所有分层规则**，preflight 原样拼进去就是一份裸规则，会压过每一个
插件的工具类：

{/* ref file="../plugins/shell/build.ts" lines="181-198" */}

**第三步：同层、同权重，谁生效只看文档顺序。** 于是问题是这样发生的——甲插件的元素上
带着两个类，一条管四边、一条只改左右；乙插件只用到了前者，所以**乙的表里没有后者**；而乙的表
**后加载**。层里的顺序就成了「甲的①、甲的②、乙的①」，乙那条①排在甲的②后面，**把甲的元素
整个重置回①的样子**。

**而且没有任何一处报错**：两张表都编得对、都加载成功了，只是互相覆盖了。构建是绿的，控制台
是干净的，页面上只有「这块怎么跟我写的不一样」。

这一下发生在时间上，写成文字必然是一串「先……然后……于是……」，所以画了一遍：

**所以隔离是必需的，不是过度讲究。** 这条判据从头到尾没被推翻过，换过的只是**隔离的手段**。

### 隔离靠名字，不靠位置

隔离两张表，直觉上的办法是**按位置**：把甲插件那张表里的每条选择器都改写成「只有待在甲插件那个
容器底下的元素才算」。这条路走过，也被换掉了。换掉的理由不是它不管用，是它的**失效点在
运行时**：

- 弹出层默认 portal 到 `<body>` 上，一放出去就不在那个容器底下了，整个菜单一个类名都不生效
- 外壳的根是每个窗格的祖先，所以外壳那张表的规则对所有窗格里同名的元素照样成立
- 哪张表先注入页面决定谁覆盖谁，而那个顺序是运行时才定的

三种都不报错。**DOM 的位置是运行时才确定的**，所以按位置隔离，等于让隔离依赖一堆隐含前提，
前提破了没有任何人会告诉你。

现在这条路是**按名字**：让类名从源头就唯一（每个插件一个短前缀，类名长成 `baseui:flex` /
`shell:flex` 这种）。规则仍然全页有效、跟 DOM 祖先关系无关，但**它只可能匹配到本插件画出来的
元素**——因为别的插件根本不会写出这个名字。

这一换，失效点从运行时挪到了写代码那一刻：

| | 按位置隔离 | 按名字隔离 |
| --- | --- | --- |
| 靠什么隔离 | DOM 祖先关系 | 类名的唯一性 |
| 弹出层 portal 出去 | 整层没有样式 | 无关，照样有样式 |
| 加载顺序 | 是隐含前提 | 不参与 |
| 会怎么坏 | 三种，全部静默 | 只剩一种：忘写前缀 |
| 什么时候看得见 | 某个弹层被打开、某两个插件同时装上的那天 | **当场**——那个类不生效，写的人打开页面就看见 |

「忘写前缀」还能用一条守卫测试拦住（第四节），而上面那三种一条都拦不住。

**工具链原生支持这条路**，不用自己改写：Tailwind 4 的 `prefix()` 写在拆开的主题导入上、
shadcn 的 `components.json` 里有 `tailwind.prefix`、`cn` 那个包（tailwind-merge）对带前缀的
类名本来就合并得对。按位置那条路则是我们自己写的 postcss 改写，外加给每个带弹出层的组件打补丁
——两份要自己维护的成本，换来的隔离还更弱。逐条测量数据与决定经过在[定过的事](/docs/decisions)。

### 第三问：组件——共享的是源头，不是运行时

按钮、下拉菜单这些东西，两个插件长得一模一样，靠的**不是**它们运行同一段代码。

每个插件自己有一份 `components.json`，要什么组件就从 shadcn 官方拉什么，**拉下来就是这个插件
自己目录里的一个 tsx 文件**，跟着这个插件一起被 esbuild 打包进它自己的产物：

{/* ref file="../plugins/baseui/components.json" lines="6-12" */}

那两个插件的按钮长得一样，是因为**源码来自同一处**（同一个 registry、同一个 `style` 与
`baseColor`），而颜色**读的是同一份令牌**。运行时它们是两段互不相识的代码。

这么做的代价是每个插件的打包产物里各有一份按钮的字节。买到的是：一个插件想改自己那颗按钮，
改自己目录里那个文件就行，**不用发一个共享包、不用等别人升级、也不可能改坏别人的**。
「共享一个组件库」这条候选否掉的实测理由在第五节。

`prefix` 那一行让 CLI 直接写出带前缀的类名，所以拉下来的组件不用手改。这也是隔离改用前缀之后
顺带得到的好处：以前为了把弹出层放回容器里，拉下来的组件得逐个打补丁，现在**重新拉取官方原版**。

### 还有一份东西要共享：React 实例

上面三问都是 CSS 的事。JS 这边只有一样是共享的——react 那一族。

机制是页面级的 **importmap**：提供方在自己的包清单里声明「我给页面提供这几个裸名」，

内核扫这份声明拼成一张表，在外壳第一句裸名 import **之前**注入页面，**只注入一次**。
**内核不认识 `react` 这个词，它只转交声明**——扫描、拼装与注入时序的正本在内核仓文档站
（「内核契约面」与「取址」）。

插件那边对应的做法是：react 系四个裸名**外置**，其余依赖一律**打包进本插件的产物**——

{/* ref file="../plugins/baseui/build.ts" lines="5-14" */}

外置的判据很硬：**在 importmap 里的才许外置**。不在里头的（组件用的那些库）外置成裸名，
就是运行期一句「解析不到这个模块」。

**这份共享现在换来的是什么，要说清楚**：一是字节——带界面的每个插件不必各带一份 React；二是
**为将来留的余地**。眼下的窗格契约交给插件的是一个 DOM 容器加一个挂载函数，插件在容器里自己 `createRoot`，
**没有任何 React 对象跨插件传递**，所以「同一份实例」这件事今天并不是正确性的前提。但如果哪天
契约变成「插件交出一个 React 组件、由外壳来渲染」，那时它就是硬前提了——两份 React 实例下
hook 立即报错。现在把这条留着，比将来再统一便宜得多。

把上面几件事按时间排一遍，就是外壳启动时做的事。每一步都有它必须在那个位置的理由：

**第一步：内核注入 importmap，然后才 import 外壳的浏览器端代码。** 顺序反了，外壳顶层那句
`import { … } from 'react'` 就解析不到。

**第二步：外壳问一次 `shell.env`**，拿到 home、三张样式表的地址，外加这一刻的用户外观样式
（第四步用）。地址由 node 端算（自身的表从 `import.meta.url` 算，令牌表经 fileUrl 解析到本包自己的产物），**顺序是写死的**：
令牌、dockview、外壳自己那张。

{/* ref file="../plugins/shell/src/index.ts" lines="60-73" */}

{/* ref file="../plugins/shell/src/index.ts" lines="248-272" */}

**第三步：三张表全部注入、并且都等到加载完成，才往下走。** 令牌那张必须最先——层顺序是它声明的；
dockview 那张管的类名不经我们的手（改不了名，也就加不上前缀），所以它整张不做隔离；
外壳自己那张类名一律带自己的前缀。

**第四步：把主题插件的启动样式注入在这三张之后。** 值是第二步 `shell.env` 带来的——node 端处理

而「重启后启动即生效」要求它在第一帧之前插入页面。

**第五步：加上 `.dark`、加上身份标记，然后 `createRoot`。** 深色是默认状态，令牌的暗色那一套在这里

{/* ref file="../plugins/shell/src/client/index.tsx" lines="681-692" */}

**第六步：开一个窗格时**——从注册表里取这个插件自报的两个地址 → **先注入它的样式表、等它加载完成**

发生在样式表加载完成之前，那一瞬间是一堆没有样式的元素。这两件事因此放在同一个清理单元里——拆成两处
就只剩「谁先执行」这种靠排列顺序的默契。

## 二、模块划分与依赖方向

五块东西，箭头**全是单向的**：

| 模块 | 管什么 | 它**不知道**什么 |
| --- | --- | --- |
| 令牌表（住外壳包里） | 值：语义变量的两套值、preflight、层顺序声明 | 不知道有哪些插件，不知道 Tailwind 前缀这回事，没有 node 端（产物是两份 css，2026-09-22 起随外壳包发） |
| 每个插件自己的表 | 规则：本插件用到的那些工具类，类名带本插件的前缀 | 不知道别的插件存在，不知道值最终是多少（它只写 `var(…)`） |
| 外壳 | 转交与容器：注入三张表、给每个窗格一个容器、把这个窗格变成容器查询的根 | **不知道任何插件的类名**，也不知道插件的表里有什么 |
| 主题插件 | 用户覆盖：字体两项 + 一整段自定义 CSS，交给外壳在最后注入 | 不知道任何插件存在，也不知道外壳把它注入在第几位（它只交出一段字符串） |
| 内核 | 只转交共享声明，拼 importmap | 不认识 `react`，不认识任何类名，不认识任何包名 |

依赖方向是：**插件 → 令牌**（构建期引映射面、运行期读页面上那份值），**插件 → 外壳**
（注册窗格时报自己那两个地址），**外壳 → 主题插件**（一条软契约命令），**内核 → 谁都不依赖**
（它只读清单字段）。反向的箭头一条都没有：

- 令牌表不知道有哪些插件，所以加一个插件、删一个插件，它一个字都不用改
- 外壳不知道插件的类名，所以插件改自己的样式，外壳不用重新构建
- 主题插件不知道谁在用它的启动样式，外壳没装它就没有这一步，它自己照常运行

**换掉实现要不要改调用方**，逐个问一遍都过得去：令牌把 zinc 换成别的底色，插件一行不改；
一个插件把自己的表从头重写，外壳一行不改；主题插件被另一个插件替换（只要还响应那条命令名），
外壳一行不改。

## 三、接口划分

这一层是**契约**：变了就得所有人跟着变，所以要一条条引用源码写明。

### 令牌的契约有两个面，缺一不可

**声明面**（页面加载的那张）交出去的是一份**变量名清单**——`--background` / `--primary`
这些名字。这份清单**只加不删**：删掉一个名字，所有插件的表里那条 `var()` 立即读到空值，而读到空值是
静默的。

**映射面**是插件在构建期引的那份，它把「类名怎么解析到变量」这件事告诉编译器，但**一个变量
声明都不输出**：

{/* ref file="../plugins/shell/src/tokens/theme.reference.css" */}

两个面**必须是两个文件**，理由写在它自己的文件头注释里（下一节展开）。插件那边引的形态是固定的一行，
第六节抄得到。

### 窗格注册时交出去的两个地址

插件把自己浏览器端脚本与样式表的位置告诉外壳，值从自己的 `import.meta.url` 算成 `file://`：

{/* ref file="../plugins/shell/src/pane-registry.ts" lines="27-30" */}

`style` **是可选的**——插件可以没有样式表，那是正常情况而不是错。取不到也不抛，调用方照常注册它。

### `shell.env`：启动时要的三张表、外观样式与版本

外壳浏览器端启动时调一次的那条命令，返回的是 home、一个**有序**的地址数组、可有可无的
`startupCss`（用户外观样式，主题插件没装或没设就没有这一项），外加状态栏显示版本用的
`versions`（必有，见[外壳](/docs/shell)状态栏一节）。顺序本身就是契约的一部分
（令牌必须第一张），正本是上一节第二步引用的那段。

### 层顺序与 preflight，为什么由令牌表来管

**这段说明什么**：插件的表只写工具类那一层、不声明层与层的先后，所以顺序只能由**先加载的那张**

## 五、取舍与结论

决定经过、验证的数据、迁移的那几次提交，全在[定过的事](/docs/decisions)的 2026-09-09 那条，
这里不重复。这一节补两样那条没展开的：**否掉的候选**与**残余的耦合**。

### 否掉的三个候选

**Shadow DOM。** 最彻底的隔离，每个插件一个 shadow root，样式天然出不去也进不来。否掉有两条：
一是 `@property` 声明在 shadow root 里被忽略，而 Tailwind 4 的内部机制大量用它；二是弹层
组件的「点外面关掉」那类判断在 shadow 边界上有一堆历史问题。**为了一层隔离，把组件生态的
可用性押上去，不划算**——何况值本来就该穿透，shadow 恰恰把值也挡在外面。

**共享一个组件库。** 所有插件从一个包里 import 按钮。母仓实测过：**CSS 一分没省**——因为每个插件
仍然要为自己用到的类编一张表，共享的只是 JS 那点字节；换来的是一条硬依赖，那个包升一次版
所有插件都得跟。

**每个插件全自带。** 连令牌也各带各的。那样**主题的一致性无从保证**：几个插件几份颜色值，
换主题要所有插件一起重新构建、一起发版。这条恰恰是「值必须全页共享一份」那一问的反证。

### 否掉的是共享运行时，共享源码的通道留着

「共享一个组件库」否掉的是**运行时**——所有插件从同一个包 import。但「生态将来要不要
自己的组件源头」这条路没有跟着关掉：shadcn 的 registry 本身是**可自建的开放协议**，
官方那份只是它的第一个实现。

- **协议同构。** 自建与官方是同一份 `registry.json` schema，消费端是同一个 `shadcn add`
  （按 URL，或登记进 `components.json` 的命名空间）。这个关系的形状本生态天天在用：
  官方 npm 源与本机 Verdaccio，就是同一协议的两个实现。
- **前缀改写是协议自带的。** registry 里的组件源码一律无前缀，CLI 拉取时按**消费者自己**
  `components.json` 里的前缀改写类名——跟今天从官方拉组件是同一个动作：

{/* has file="../plugins/baseui/components.json" text="baseui" */}

  所以同一份源码拉进任何插件都自动带上那个插件的前缀，值照旧读令牌表。**今天立的全部纪律
  已经把将来加源头、换源头的路留好了，启用那天零架构变更。**
- **版本管理要自己做。** registry 是一份静态清单：无版本语义、没有 lockfile，不固定引用
  就是浮动依赖——要可复现，固定到 tag 或完整 commit SHA。而且拉下来就是消费者自己的代码，源头修了
  bug 不会自动到达，各插件要各自重拉。
- **什么时候值得建，只看一条**：同一个组件在两个插件里各复制了一份、并且开始各自漂移的那天，才
  值得建。在那之前，官方源头 + 各拉各的已覆盖全部需求——插件作者不需要为「组件怎么共享」
  操心任何事。

### 残余的耦合，一条

**Tailwind 内部那批 `@property` 不随前缀走。** 每张表各注册一遍同名的那批，同名后注册的
赢。所以**全生态仍然得同一个 Tailwind 大版本**——这条不是前缀方案引入的，但前缀方案也没消掉
它。

还有一条明显的代价：**源码里每个类多一个前缀**，一直要付。

## 六、写一个带界面的插件

原理讲完了，做法就很短。

**一、`components.json` 填两处**：`tailwind.css` 指一个真实存在的样式入口路径（这个字段是
必填的，省略的话会报一句没有细节的错），`tailwind.prefix` 填本插件的短名——CLI 拉下来的组件因此自带
前缀，一处都不用手改。形状照第一节引用的那份抄。

**二、写那五行样式入口。** 照第四节引用的那五行原样抄，只把前缀换成本插件的短名。四条 import
一条都不能省。

**三、构建脚本补一步**：编译本插件那张表，输入就是那份入口，扫描面由入口里最后那条说了算。

**四、拉组件**：`shadcn add` 什么就有什么，拉下来是本插件目录里的文件，跟着本插件一起打包。
组件的运行时依赖**打包进本插件的产物**，别外置（不在 importmap 里的裸名，外置就会在运行时报错）。

**六、抄两条守卫**：忘写前缀那条、产物形状那条。第四节都引用了出处，照抄换个前缀就行。

### 会静默出事的那几件事

这一类有个共同的性质：**「编不出规则」在编译器眼里跟「这不是个类名」是同一回事**，
所以它们全都不报错。

| 干了什么 | 现象 | 怎么防 |
| --- | --- | --- |
| 入口里没引令牌的映射面 | 颜色类**整个是空的**——语义色编不出对应的变量引用 | 五行入口一行不省 |
| 入口里没引动画那个包 | 动画那一类类名一个字节都不输出，菜单打开关闭没有过渡动画 | 同上 |
| 类名忘了带前缀 | 那个类不生效，页面上就是那一处没样式 | 前缀守卫 |
| 标记类（当锚的那种）没带前缀 | 变体的选择器**永远不命中**，类名和规则都在，只是对不上 | **守卫检查不出来**，只能靠知道这条 |
| 在插件的表里写 `:root { --primary: … }` | 要么覆盖了全页，要么跟别处不一致 | 令牌是页面共享的那一份，插件的表里不碰它 |
| 想按窗格宽度换布局，却写成了视口断点 | 按整窗大小判，拖窄这个窗格毫无反应 | 用容器查询变体（带 `@` 的那种），根是外壳给的容器 |

最后一条值得多说一句：**窗格不是视口**。这条线上一个插件可能被拖成 300px 宽的一条，也可能占
满 1000 多像素，而整窗大小自始至终没变过。插件里的响应式判据要问的是「我这个窗格现在有多宽」，
不是「这个窗口有多大」。
