# 系统地图

**本页回答**：`gwb-ui-plugins` 拆成哪几个模块、各在哪、模块之间谁依赖谁、新来的人先读哪个。

## 模块

一行一个模块。「在哪」是包根（`dist/` 是生成物，`build.ts` 在各包根下打各自的产物）：

| 模块 | 在哪 | 管什么 | 先读 |
| --- | --- | --- | --- |
| 外壳 | `plugins/shell/src/` | 窗格注册服务（node 端）＋ 多个 dockview 窗格容器（well，代码模块 `well-hub`；浏览器端）——内核页面根的唯一入口 | [外壳](/docs/shell) |
| 外观 | `plugins/theme/src/` | 全局启动样式（字体＋自定义 CSS）＋「外观」窗格；没有外壳也照常加载 | [样式与组件](/docs/styles) |
| 基础界面 | `plugins/baseui/src/` | 基础插件的官方窗格集（日志、插件管理），一个插件多个窗格、浏览器端按 `pane.id` 分派 | [样式与组件](/docs/styles) |
| 令牌 | `plugins/shell/src/tokens/` | 语义变量亮暗两套＋preflight＋层顺序声明；没有 node 端代码，产物是外壳包里的两份 css（`theme.css`、`theme.reference.css`） | [令牌与颜色](/docs/tokens) |

「一个 UI 平台的整体，要换整套换」——四个模块放在同一个仓、一起换的立场与判据在[样式与组件](/docs/styles)。

三个插件包的构建方式相同：`build.ts` 先清空 `dist/`，node 侧与浏览器侧都用 esbuild 各打成一个文件，浏览器侧的
外置名单从内核包的页面入口读；外壳另用 tsc 只输出声明（包根与子路径 `./pane`）。仓根的 pnpm workspace 只收
`plugins/*`，仓根 `pnpm build` 只构建这三个插件；文档站 `docs-site/` 是独立的 pnpm 工程，自带 lock，在站目录里 install：

## 依赖方向

单向，四条依赖：**插件 → 令牌**（构建期引用映射文件 `theme.reference.css`、运行期读页面上那份变量值）、**插件 → 外壳**（注册窗格时提供两个地址；浏览器侧 `import type` 外壳子路径 `@godcreator/gwb-shell/pane` 的类型，见[外壳](/docs/shell)「类型从 `@godcreator/gwb-shell/pane` 引」一节）、**外壳 → 主题插件**（一条可选命令，外壳没有它也照常运行）、**本仓 → 基础仓**（用基础插件的服务与类型，基础仓不依赖本仓）。逐模块的「它不知道什么」那张表在[样式与组件](/docs/styles)第二节。

## 包清单里的依赖

peer 怎么写、每个插件注入了哪些服务、按名字调用了别家哪些命令，见[插件之间怎么连](/docs/wiring)。

## 各页怎么分

本仓的现状页按功能线组织、不按包分：[外壳](/docs/shell) 一页，[样式与组件](/docs/styles) 一页覆盖
theme / baseui / 令牌的契约与原理，以及页面上的 react 从哪来，[令牌与颜色](/docs/tokens) 是令牌规则的
正本，[遇到过的问题](/docs/walls) 记录这个仓遇到过的问题。
