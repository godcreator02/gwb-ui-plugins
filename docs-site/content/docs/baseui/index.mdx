包 `@godcreator/gwb-baseui`，在 `plugins/baseui/`：node 侧入口 `src/index.ts`，`logger.query` 的参数校验与读文件在 `src/log-query/`，
浏览器侧入口 `src/client/index.tsx`，窗格在 `src/client/panes/` 下各占一个目录，共用的组件在 `src/client/components/ui/`。

## 功能

**整套基础插件的界面。** 插件管理这类基础插件只有 node 侧，它们的界面统一由这一个插件提供，和基础插件一起默认全装。
它不是各个基础插件界面的临时集合：它服务的是分散在几个仓里的一整套基础插件，放不进其中任何一个插件的仓。
眼下的窗格：

| 窗格 | id | 什么时候有 | 做什么 |
| --- | --- | --- | --- |
| 日志 | `logger` | 总是有；`logger.query` 不在时窗格里显示命令调用失败的原因 | 看 `gwb.log` 里最近的日志，可见时每秒取新写的；按来源与级别筛选、日志文件在哪 |
| 插件管理 | `plugin-manager` | 装了插件管理 | 装、卸、升级、启停插件与条目，改各插件的设置 |

**查日志文件的命令 `logger.query` 也由本插件登记。** 日志由内核写进 `<home>/gwb.log`（一行一个 JSON，轮转出的旧文件是 `gwb.log.1`），
日志窗格和经 MCP 入口的 agent 都调这条命令读它。本插件默认全装，所以这条命令一直调得到。为什么不单独成一个插件，
见[查日志的命令并进基础界面](/trajectory/2026-09-28-log-query-moves-into-baseui)。

**三条规矩**，破了任何一条，它就会变成什么都往里放的插件。

**一、必需依赖只有外壳，用到的基础服务一律局部注入。** 插件管理窗格跟着插件管理的服务走：缺了服务就不登记，服务后装上时补登记，服务卸载时窗格跟着注销。

**命令只有一条 `logger.query`**，`effect` 标 `read`，`plugin` 不写、由命令总线从条目取包名。日志文件的位置是内核的 `dataDir` 下的 `gwb.log`：

{/* ref file="../plugins/baseui/src/index.ts" lines="27-45" hash="28cd476cc2fc" blob="7b7e30b1a7cd" */}

参数、回执与报错以 `usage` 为准：参数 `{ limit?, minLevel?, name?, text?, after? }` 都可省，认不出的键、类型不对直接报错；
回执 `{ file, cursor, entries }`，`cursor` 是 `gwb.log` 里最后一个完整行末尾的字节位置，下一次作 `after` 传回来：

{/* ref file="../plugins/baseui/src/log-query/query.ts" lines="13-18" hash="51db280a3f1c" blob="279374238193" */}

末尾内核还没写完的半行不返回，下一次再读；日志文件是外部输入，有一行不是内核写的形状就整次报错，写明文件与行首：

## 依赖

**注入的服务**：

| 服务 | 怎么接 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- | --- |
| `gwbShell`（`@godcreator/gwb-shell`） | 必需注入，peer `workspace:*` | 登记窗格、报名字 | 本插件不加载：没有窗格容器就没有窗格 |
| `gwbCommands`（`@godcreator/gwb-commands`） | 局部注入，peer 且 `optional` | 登记 `logger.query`；类型从它的包根 `import type` | 照常加载，只是不登记 `logger.query` |
| `gwbPluginManager`（`@godcreator/gwb-plugin-manager`） | 局部注入，peer 且 `optional` | 只看服务在不在，决定登不登记插件管理窗格；回执类型从它的 `./receipts` 子路径引 | 照常加载，只是没有插件管理窗格 |
| 内核包 `@godcreator/gwb-kernel-desktop` | peer，只 `import type` | `GwbContext` 的类型；登记 `logger.query` 时取 `ctx.gwbKernel.dataDir` 定位 `gwb.log` | 类型检查不过；不在 gwb 内核里登记命令时当场抛错 |

**按名字调的命令**（经外壳交给窗格的 `host.call`，命令不在就在回执里说明）：

| 对方 | 命令 | 谁调、做什么 | 回执怎么认 |
| --- | --- | --- | --- |
| 本插件的 node 侧 | `logger.query` | 日志窗格：挂载时取最近一批，可见时每秒带 `after` 取新写的；底栏显示回执里的 `file` | 按形状逐项收窄，有一条不对就整批报错；窗格与 `src/log-query/` 互不 import |
| 插件管理 | `plugin-manager.*` | 插件管理窗格：列表、查新版本、搜索、装卸、升级、启停、增删条目 | `import type` 插件管理的回执类型，只按外层 `ok` 分开成功与失败 |
| 设置插件 | `settings.all`、`settings.get`、`settings.set`、`settings.delete` | 插件管理窗格：按条目列设置、看 secret 的明文、保存、连设置值一起删 | 按形状收窄；设置插件不写 peer |
| 外壳 | `shell.plugins`、`shell.reload` | 插件管理窗格：条目标题与图标、升级后整页重新加载 | 按形状收窄 |

`@godcreator/gwb-plugin-manager/receipts` 是第一个。两边用同一套类型，回执形状对不上在构建时的类型检查里报出来，窗格里不再按形状校验：

插件管理的下限写 `^0.14.3`：这里用到的回执类型（包括启停与删条目那种不带 `data` 的 `Acknowledged`）要这一版起才全。
`./receipts` 只有类型、没有任何 import，浏览器侧的 tsconfig（只有 DOM 类型）能直接引。为什么用到的插件都写 peer，见[用到的插件写进 peer](/trajectory/2026-09-25-plugins-as-peers)。

## 不做的事

**不把窗格移到各个基础插件的仓里，也不给每个基础插件各发一个界面包。** 一个界面插件管全部基础插件；基础插件的回执变了，用上面「导出回执类型」的做法，不移窗格。

**不给说明书、命令总线、MCP 入口加窗格。**

**不收功能插件的界面。** 界面本身就是全部功能的插件自己登记窗格。

**除了登记 `logger.query`，不调基础插件服务上的方法。** node 侧只调命令总线的 `register`；注入插件管理的服务只为判断它在不在；
窗格的所有操作经命令总线按名字调，窗格在页面上也拿不到 node 侧的服务。
