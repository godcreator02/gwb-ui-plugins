`gwb-ui-plugins` 放着 gwb 工作台界面层的三个插件：外壳 `@godcreator/gwb-shell` 接管内核的页面根、提供窗格容器与窗格注册，
外观 `@godcreator/gwb-theme` 管全局字体与自定义 CSS，基础界面 `@godcreator/gwb-baseui` 是基础插件的官方窗格集。
三个插件、令牌表和页面用的 React 是一个整体，要换整套换，不为假想的第二个外壳维护独立的契约包（[建仓理由](/trajectory/2026-09-12-gwb-ui-plugins)）。
下面这张图画出三个插件对外的能力，以及它们和内核、基础插件、别的带界面的插件之间靠什么接上。

<SeamMap />

编号按依赖方向排：1–4 是插件接内核，5–9 是插件接基础插件，10–13 是外壳交给带界面的插件的出口，14、15 两条只靠命令名与字符串对上。
人只经页面使用这一层：看到的窗格容器、状态栏、每个窗格都画在外壳接管的页面根里。

## 接缝

### 1 接口类型

**连接的模块**：外壳、外观、基础界面的 node 侧，与内核包 `@godcreator/gwb-kernel-desktop`。

**接口**：三个插件从内核包的包根 `import type` 上下文类型 `GwbContext`，外壳另取内核服务的类型 `GwbKernelApi`；三个插件的 peer 都写内核包。
外壳取内核服务不经 inject，在构造时调 `requireKernel`：

{/* ref file="../plugins/shell/package.json" lines="30-30" hash="f587b6882de3" blob="2d44c8a19401" */}

**约定**：

- 外壳、外观、基础界面：对内核包只 `import type`，node 侧产物里不留它的包名。内核包的包根一加载就启动 Electron 应用，按值 import 等于在插件里再启动一个应用
- 内核：`ctx.gwbKernel` 由内核提供在根上下文上、不会撤销，所以插件不把它写进 inject；不在 gwb 内核里运行时外壳当场抛错

**不负责的事**：插件和运行中的内核兼不兼容，由插件管理拿 peer 里内核包的范围去比，三个插件自己不检查。

**测试**：三个插件各自的产物测试查 node 侧产物里按值 import 的包名，外壳只许 `cordis`，外观与基础界面一个都不许有：

### 2 外壳接管

**连接的模块**：外壳的页面入口 `client.js`，与内核的页面根。

**接口**：外壳的 node 侧把 `client.js` 的地址交给 `gwbKernel.setShell`；内核的页面根 import 这个模块，把 `#root` 交给它的默认导出，留下返回的 `{ dispose }`：

{/* ref file="../plugins/shell/src/index.ts" lines="145-151" hash="4c4709b8e5ae" blob="d8029385df74" */}

{/* ref file="../plugins/shell/src/client/index.tsx" lines="667-688" hash="300e176c4eac" blob="9b2b1fdf837c" */}

**约定**：

- 外壳：`setShell` 包在 `ctx.effect` 里，外壳卸载时自动交还页面根。默认导出同步返回 `{ dispose }`，`dispose` 返回时 React 树已经卸载完；异步的准备（问 `shell.env`、加载样式表、取注册表与布局文件）还没做完就被 `dispose`，挂载那一段永不执行
- 内核：后调用 `setShell` 的替换先调用的；换外壳时先调旧外壳的 `dispose`，紧接着清空 `#root`，再挂新外壳；没有任何插件调用 `setShell` 时页面显示只读状态页

**不负责的事**：窗口怎么开、页面在哪个窗口里由内核负责；内核不认识窗格与桌面，那些全在外壳的浏览器侧（见[外壳接管](/docs/shell/takeover)）。

**测试**：`setShell` 收到本包 `client.js` 的地址、外壳卸载时撤销；`dispose` 返回之后清空容器不再出错：

**约定**：

- 外壳：先登记再接管页面根，登记同样包在 `ctx.effect` 里；`dist/react/` 由 `scripts/build-react.ts` 构建，`react-dom` 的两个文件把 `react` 外置，和 `react.js` 用同一个实例；打开任何窗格之前都先等 `prepareImports`
- 内核：一批包名原子登记，同名同地址复用，同名不同地址抛错；页面上已经注入的地址变了或被撤销，`prepareImports` 拒绝，只能整页重载

### 5 命令登记

**连接的模块**：外壳命令、外观的命令，与命令总线 `gwbCommands`。

**接口**：`gwbCommands.register({ name, description, usage, plugin }, handler)`。外壳把命令总线写进 `static inject`，外观写进 `inject`：

{/* ref file="../plugins/shell/src/index.ts" lines="93-95" hash="79c3f058b1f5" blob="d8029385df74" */}

{/* ref file="../plugins/shell/src/index.ts" lines="168-171" hash="b3ebb9af8569" blob="d8029385df74" */}

{/* ref file="../plugins/theme/src/index.ts" lines="30-31" hash="82c708c0994f" blob="8a696cae264c" */}

**约定**：

- 外壳：命令总线是必需依赖。窗格在 node 侧注册、在页面上打开，注册表只能经命令传到页面，没有命令总线外壳就不加载，cordis 在日志里写明它在等谁
- 外观：命令总线也是必需依赖，登记 `theme.startupCss`、`theme.values`、`theme.save`
- 两者：`plugin` 写自己的包名；参数由各自的处理函数校验，不合格回 `{ ok: false, error }`
- 命令总线：注销登记在调用方的上下文上，插件卸载时它的命令自动注销；处理函数抛错也 resolve 成 `ok: false` 的回执

**不负责的事**：命令总线不校验参数、不认识命令的含义；谁有权调哪条命令不在这条接缝上，命令总线对所有插件开放。

## 三个插件

- [外壳](/docs/shell)：接管页面根，提供窗格注册、窗格容器与多张桌面、状态栏，随包发布令牌表、页面用的 React 和给写界面的人读的说明书 `gwb-shell`
- [外观](/docs/theme)：三项外观设置拼成启动样式交给外壳，有外壳时提供「外观」窗格；没有外壳也照常加载
- [基础界面](/docs/baseui)：日志与插件管理两个基础插件的窗格，装了哪个就登记哪个；两个窗格互不 import，只共用组件层
