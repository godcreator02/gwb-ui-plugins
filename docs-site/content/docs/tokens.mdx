# 令牌与颜色：共享规则

本页是**规则正本**：颜色怎么分级、令牌怎么演进、插件自己的样式能做到哪一步。原理（为什么值全页
一份、映射文件怎么工作、开机怎么注入令牌表）在[样式与组件](/docs/styles)，本页不重讲。**现存代码
有未追平这些规则的，以本页为准追平；追平之前不改本页迁就现状。**

## 一、两级：跨插件共享的语义归全局令牌，插件自己的视觉归插件

样式分两级，判据只有一条：**这批样式要不要跨插件一致、要不要跟工作台主题走。**

| | 全局令牌（外壳包里的令牌表） | 插件域样式 |
| --- | --- | --- |
| 管什么 | **跨插件共享的语义**：背景、前景、主色、卡片、边框、muted、状态色 | 插件自己产品里的视觉词汇——编辑器的高亮色盘、专属图示色这一类 |
| 几份 | 变量值文件（`tokens.css`）全页**只有一份**，由外壳注入 | 写在插件自己的产物里，各插件各一份 |
| 跟主题 | 换值后所有插件一起变 | 默认不跟；派生自全局令牌的那部分自动跟着变 |

**「全页只有一份」只说全局令牌这一级**，不是「所有样式词汇都收进令牌表」——把插件域样式也
塞进令牌表，跨插件共享的那批名字就混进了只有一个插件在用的东西。

### 归哪一级：三个问题，从成本最低的问起

拿到任何一个新样式值，依次问，问到哪一级就停在哪一级（**先问「能不能不升为全局令牌」**，别反过来）：

| 问 | 停在哪一级 | 典型 |
| --- | --- | --- |
| 一次性装饰？ | **任意值写死**（`bg-[oklch(…)]` 或插件内一段 CSS），完事 | 一处用的小点缀 |
| 插件内多处用、只有本插件有这个视觉概念？ | **插件域令牌**（见第四节） | 日志来源圆点的颜色、编辑器高亮色盘 |
| 跨插件要一致、主题要管？ | **全局令牌** | 警告色、间距基数、阴影刻度 |

插件域令牌**什么时候升为全局令牌**：第二个插件也要用它的那天（跟组件源头的判据相同）。

## 二、颜色的分级判据

拿到任何一个新颜色，先问一句：**换主题时它该不该变？**

| 判据 | 性质 | 做法 |
| --- | --- | --- |
| 该变，且跨插件要有同一含义（警告、危险、品牌） | **语义色** | 升为全局令牌：`tokens.css` 加值（亮暗两套）、`theme.reference.css` 加映射，发版；插件升依赖、重新构建后写语义类 |
| 该变，但眼下只有本插件在用 | 先用已有的语义色 | 这种颜色多半就是 accent / muted / destructive 的别名；确实没有对应的再考虑加令牌 |
| 不该变（纯装饰，明确不跟主题） | **装饰色** | 明确写死：任意值语法或插件内一段普通 CSS，要答得出「它为什么不跟主题」 |

**三条禁止**：

1. **禁止用 Tailwind 内置调色板的类表达语义色**——调色板查的是 Tailwind 出厂的颜色表，不查令牌表，
   换主题不跟着变，而且不报错
2. **禁止把语义色写成字面值**（hex / oklch）——理由同上
3. **禁止插件自带一套私有的令牌包**——插件自己的「映射文件＋变量值文件」等于再造一张令牌表：值进不了
   页面上唯一那一份，换主题换不到它；要让外壳注入它就得改外壳，又回到集中登记。全生态只有一张令牌表，
   特殊颜色只有上表那两种写法

## 三、令牌的三条演进规则

令牌的名字清单是**全生态的公共契约**，演进只许两个方向：

1. **改值随便**——那是主题的本职。改 `tokens.css` 里的值、发版、home 升级，所有插件不用重新构建就当场变
2. **加名字随便**——向后兼容。加了新令牌，不用它的插件什么都不用做；用它的插件升依赖、重新构建
3. **不许删名字**——删掉一个名字，所有还写着那条 `var()` 的插件**当场读到空值，而且不报错**。名字
   一旦发出去，只能标成废弃、继续保留

## 四、插件域令牌怎么写：值与注册分两处

插件有自己的视觉体系**完全合法**（界面复杂的插件必然如此），写法分**两处**，都在插件自己的包里：

1. **值**写在 `src/client/tokens.css`：插件域变量的声明（名字带插件前缀，不和全局令牌重名；写在 `:root` 上，
   portal 到别处的浮层也读得到）。优先派生自全局令牌（`--插件域变量: var(--accent)`），只在少数需要
   不一样的地方单独给值；要亮暗各一套，用 `.dark` 当祖先写覆盖规则——产物守卫预期并放行这种写法。
2. **注册**写在样式入口末尾：追加 `@theme inline { --color-插件域名: var(--插件域变量) }`，注册本插件
   专属的颜色类（`baseui:bg-src-plugin` 这种）；`inline` 让产物直接引用插件域变量，键名被前缀改写也
   不影响，产物里没有字面默认值。

现成的例子：baseui 的日志来源圆点颜色（`src/client/tokens.css` + 样式入口末尾那段 `@theme inline`）。
另有一条照旧：**窗格标题、工具栏、设置面板这些工作台级的界面不算插件自己的视觉**，照常用语义类。

## 五、主题的规矩

1. **主题只改令牌的值，永远不改规则**——写了某个具体插件选择器的主题，那个插件一升级就失效
2. 亮暗就是同一批名字的两套值（`:root` / `.dark`），没有别的机制；用户自己换外观走 theme 插件
   的自定义 CSS，它的优先级高于一切分层规则
3. 主题完整的前提是**令牌表之外没有写死的值**：生态里每多一处写死的语义色，就多一处主题永远换不到
   的地方

## 六、守卫

第二节的三条禁止，由每个插件的产物守卫检查（`tests/artifact.test.ts`）：

- **没有字面默认值**：产物里 `var()` 的默认值只能是另一个 `var()` 引用或 `currentcolor`
  关键字，出现字面值就失败。tw-animate-css 包里写死的动画缺省值（`--tw-animation-*` /
  `--tw-enter-*` / `--tw-exit-*` / 简写里的 `--tw-ease,ease`）除外——那是动画机制的运行时
  默认，不是设计值，映射文件也改不到
- **颜色类白名单**：颜色类选择器里的颜色名必须在「令牌映射文件里的条目 ∪ 本插件样式入口里
  `@theme` 注册的」之内——**两边都在测试时现读现解析，不手写名单**，令牌加了名字或插件注册了
  新颜色，守卫自动放行。特殊颜色名（transparent / inherit / current）与不是颜色的写法（字号、对齐、
  边的方向、宽度）不查
- **检查范围**：只管 Tailwind 颜色类这一种；插件域变量与普通 CSS 规则不在检查范围内，第四节的
  插件域令牌不受影响；任意值写死（`bg-[oklch(…)]`）是明确的装饰色写法，也不查

Tailwind 出厂刻度也收进了令牌表：出厂主题里被用到的键全部经映射文件给值，间距、字重、字距、白与黑、
全部阴影、过渡、容器断点都能随主题换——**升 Tailwind 大版本时，照 `theme.reference.css` 头注核一遍
键名**。
