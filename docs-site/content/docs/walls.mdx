# 遇到过的问题（界面侧）

**本页回答**：这个仓的代码为什么这样写——每一段是一个遇到过的问题。从 gwb-base-plugins 站的同名页迁来（2026-09-12 三仓拆分）；引用路径相对本仓根。没有界面的那部分问题（服务、发版、MCP 与 skill）在 gwb-base-plugins 的站上，装配验收的问题在验收仓。

## 服务

### 窗格释放总线句柄时没注销监听函数——每个窗格只开一份时这个问题看不出来

窗格间总线的 `release()` 曾经只减引用计数、分组空了才整个删除。**每个窗格只能开一份时这完全看不出
问题**：最后一个窗格释放句柄时分组就删了，监听函数注销没注销都一样。

同一个窗格能开两份之后问题就出现了：关掉两份里的一份，**它注册的监听函数仍留在分组里**（另一份还占着
这个分组），于是关掉的那个窗格继续收到事件，回调作用在一棵已经卸载的 React 树上。症状要么是 console 里
「往已卸载组件 setState」的警告，要么是不报错的内存泄漏。

这是**新功能暴露出来的旧缺陷**，不是新代码写错的。现在句柄自己记着注册过哪些监听函数，`release` 时
先逐条注销、再释放——顺序反过来的话分组可能已经删除，注销不起作用，而分组没删除的情况正是这几行
要解决的。

{/* ref file="../plugins/shell/src/client/bus.ts" lines="90-99" */}

同时定下的两条语义：`emit` 在 `release` 之后**什么都不做、也不报错**（外壳的清理顺序是「先让插件
dispose、再 release」，所以插件在自己的 dispose 里 emit 一条仍然有效）；分组里存监听函数用的是 `Set`，
**按函数引用去重**，两个窗格注册同一个函数只存一份，谁先注销就移除了。

### 条目 id 自带 `home:` 前缀，别去掉它

`fiber.entry.id` 取到的**不是** `hello`，是 **`home:hello`**——loader 把插件的条目嵌套在
`cordis:include` 那条下面，id 是从根到它的全路径（内核那条 include 的 id 就叫 `home`）。

**这不是出了故障之后查出来的**，是 `gwb-shell` 第二阶段在隔离 home 里实际运行验证时，从 CDP 探针脚本的
返回结果里直接看到的：窗格 id 本来按 `plugin:<entryId>:<窗格 id>` 设计成三段，实际拼出来是四段的
`plugin:home:hello:main`。

看着不好看，但**去掉那个前缀会出错，而且出错时没有任何现象**：`entryId` 要跟条目的 `id` 完全一致——
注册表按它登记，`openPane` 的安全边界也按它判断「哪几个窗格属于这条条目」。改短了就跟注册表里的记录
对不上，症状是不报错地匹配到错的窗格：认不出自己开的那几份，也认不出别人的，两边一起错位。

所以窗格 id 是个**不透明的键**，不要从中拆出各段。要 `entryId` 或 `paneId` 就从面板的 `params`
里取，那儿本来就分开存着。

{/* ref file="../plugins/shell/src/openable.ts" lines="102-105" */}

### `typeof` 一个类是 `function`，按「是对象」判断它就等于不存在

`shell.reload` 0.2.2 与 0.2.3 实际运行时都返回「不在 Electron 主进程里」，而探针脚本（用 electron.exe
运行，放在应用目录外与 `node_modules/.pnpm` 下两个位置）证明 `import('electron')` 的命名空间与 `default`
上都有 `BrowserWindow`，`createRequire` 也拿得到。根因在取值方式：`BrowserWindow` 是一个**类**，
`typeof` 是 `'function'`，而那句 `isRecord(bw)` 只认 `typeof === 'object'`——于是 `getAllWindows`
永远是 undefined。0.2.3 以为是 ESM `default` 导出方式的问题，改错了地方；0.2.4 才改对：对象或函数都继续往下取。

{/* ref file="../plugins/shell/src/reload.ts" lines="32-47" */}

**判据**：凡是按形状收窄一个「可能是类」的东西（`BrowserWindow`、`Service` 子类、任何构造器），
`isRecord` 那种「是对象」的类型守卫要配上 `typeof === 'function'`；而且**报错要说清是哪一层没认出**
——「没有 X.y」分不开「X 不在」和「X 在但 y 不在」，这次多发了一个改错的版本就是这么来的。

### 外壳换版本时渲染层报 `removeChild` NotFoundError——两层是同一个原因

**现象**：运行中换 shell 版本（`plugin-manager.update-all` 或 `devkit.dev`，client.js 地址变了）
的那一刻，渲染层报 `Uncaught NotFoundError: Failed to execute 'removeChild' on 'Node'`，条数＝1 +
开着的 React 窗格数；整页重载后不再出现。同版本 remount 不复现——地址没变时，内核页面根那段检查
根本不会换外壳。

**根因**：「先清空容器、后卸载 React 树」，两层各有一处。
1. 外壳层：旧 `dispose` 把 `reactRoot.unmount()` 放在 Promise 链上（微任务），同步执行的那部分已经
   清空了根节点，内核页面根随后也清空一遍；卸载 React 树发生在清空之后
2. 窗格层：`PluginPane` 的清理 effect 跑在外壳的 React 提交里，插件的 `dispose` 在那里同步调
   `root.unmount()` 会被 React 推迟，插件紧接着执行的 `container.textContent = ''` 先执行了。普通关窗格
   也走这条路径

两条都在实际运行的页面里单独复现过（先清空后卸载必报错、先卸载后清空不报；在提交内卸载必报错、移到
提交之外不报）。

**修法**（0.7.2）：外壳的 `dispose` 同步卸载完（准备与挂载 React 树分成两段，还没挂载就不再挂载）；
插件的 `dispose` 移到提交之外调用。内核换外壳的顺序不用改。**从旧版外壳换下来的那一次仍会报错**——
报错出自被换下那个版本的 `dispose`，从 0.7.2 起换成别的版本才不再报。

## 提交前检查

### 两条 oxlint 误报，都出在「有意违反规则」的代码上

迁移 shell 那批纯逻辑时遇到两条。**规则本身没错，是这两处代码故意违反它**：

{/* ref file="../plugins/shell/src/client/bus.ts" lines="68-80" */}

- **`unicorn/no-useless-spread`** —— `for (const listener of [...listenersOfType])` 那份拷贝是有意的：监听函数
  收到事件后注销自己是常见情况，直接遍历正在被修改的集合会漏掉或重复。规则看不出「遍历期间集合会被改」
- **`unicorn/no-thenable`** —— 测试里 `describeHandle({ then() {} })` **故意**造一个

只有 disable 没有理由的话，下一个人只会以为是图省事绕过去的。

**不改全局配置**：内核仓 decisions 页选定 oxlint 时判断过，白名单的真正代价是「新规则永远进不来」。
拿 111 条 correctness 规则去换这两条误报不划算。这也是那条决策第一次被实际检验：代价确实
只是「几条误报要处理」。

## 令牌

### preflight 必须放进 `@layer base`，否则它的优先级高于所有插件的工具类

{/* ref file="../plugins/shell/build.ts" lines="181-186" */}

CSS 里**未分层的规则优先级高于所有分层规则**。插件的样式表只写 `@layer utilities { … }`、自己
不声明层顺序，所以顺序得由先加载的令牌表来声明；而 Tailwind 的 `preflight.css` 是一份
**不在任何 `@layer` 里的规则**，原样拼进去就是未分层的，会覆盖每一个插件的工具类。

### 变量值与类名映射必须拆成两个文件

{/* ref file="../plugins/shell/src/tokens/theme.reference.css" lines="1-2" */}

`theme(reference)` 只阻止 `@theme` 块的输出，**阻止不了普通规则**。把写着 `:root { --background: … }`
的变量值文件（tokens.css）一起引进插件的构建里，每个插件的样式表都会多出一整份 `:root`，与页面上令牌表
那份并存，成了两份变量值。

拆开之后：映射文件（theme.reference.css）让类名能解析（`bg-primary` → `var(--primary)`），值仍在运行时
取页面上令牌表的变量。实际测量验收插件的产物，`:root` 出现 **0 次**。

## 验收方法

### 测颜色前先关掉过渡——「等过渡结束」不可靠

shadcn 的 button 基础类里有 `transition-all`。切换 `.dark` 之后立刻 `getComputedStyle`
读到的是过渡中间色：暗色 `--primary` 应该是 `oklch(0.92 …)`，第一次验收读出来是
`oklab(0.223 …)`，看着像「切换没生效」。

**当时的办法是「等 600ms 再读」，这是错的，后来就出了问题**：同一套代码换了个组件重跑，
600ms 之后读到的是 `oklab(0.21 …)`——**过渡的起点**，一点没变。原因是探针脚本把窗口
**最小化**启动，而 Chromium 会**节流后台窗口的动画**，等多久都可能停在起点。上一次
读对纯属碰巧。

两个可靠的判据：

- **看返回格式**：过渡进行中返回 `oklab(…)`（插值空间），停下来才是原始的 `oklch(…)`。
  读到 oklab 就说明这个值不能用
- **body 与按钮读数不一致**也说明还在过渡中：body 没有 transition，它任何时候都是终值

正确的测法是**把过渡关掉再读**，跟等多久无关：

```js
const kill = document.createElement('style')
kill.textContent = '*,*::before,*::after{transition:none!important;animation:none!important}'
document.head.appendChild(kill)
```

另外：直接读 `getComputedStyle(el).getPropertyValue('--primary')` 也不受过渡影响——
CSS 变量本身不参与过渡（除非用 `@property` 声明过类型）。

### 探针脚本里别用 `requestAnimationFrame` 等帧——后台窗口里它不执行

与上一条**根因相同，表现不同**。验证亮暗切换时探针脚本写成「点一下按钮 → 等两帧 →
读颜色」，症状是 **CDP 直接超时**：`Runtime.evaluate` 一直不返回，20 秒后自己断开。
排查后才想到是 Chromium 节流后台窗口——rAF 一次都没触发，那个 promise 永远
resolve 不了。

**过渡关掉之后本来就不用等**：`getComputedStyle` 是同步的，改完类名当场读就是终值。
要等异步的东西就用 `setTimeout`（它受节流的影响没有这么大），别用 rAF。

### 探针脚本的轮询要放在 node 侧，别写在页面里——同一个根因的第三种表现

上面那条说 rAF 在后台窗口里不执行。**页面内的 `setTimeout` 轮询同样不可靠**：验证 hello 的两条
命令行工具时，写成

```js
// 在页面里跑:20 秒轮询,一次都没成
new Promise((resolve) => {
  const tick = () => { if (找到了) return resolve(true); setTimeout(tick, 200) }
  tick()
})
```

**20 秒一次都没等到**，而同一段判断在 node 侧 `await new Promise(r => setTimeout(r, 2000))`
之后一次 `Runtime.evaluate` 就读到了。原因同上：窗口没获得焦点时 Chromium 会节流页面的 timer，
而 React 的重渲染也排在那类被节流的 task 里。

**写法**：轮询的循环放在 node 侧，每轮发一次独立的 `Runtime.evaluate`，页面里只做一次同步判断。

### dockview 的标签要**反复点到成功为止**

`.dv-tab` 上 dispatch 那串 `pointerdown/mousedown/...`（见下面那条）**点得太早时照样返回成功，
但那个窗格不会切换过来**——dockview 还没注册事件监听。点一次就去等，会一直等到超时。

正确的写法是把点击本身放进轮询：每轮先看目标那个窗格的 DOM 出现没有，没出现就再点一次。

### 探针脚本判断「这次的结果」时，别用自己加的 DOM 属性做标记

验证那三个按钮时，想用 `node.setAttribute('data-stale','1')` 标记上一轮的输出、再用
`:not([data-stale])` 等新结果。**永远等不到**：React 更新时复用的是同一个 DOM 节点，
自己加的属性 React 不认识，也不会替你移除。

比对 `textContent` 变化才是可靠的。

### dockview 的标签不响应 `.click()`

探针脚本要切换窗格标签时 `tab.click()` **一点反应都没有**，而且不报错——活动标签不变，
探针脚本接着就报「找不到那个窗格里的按钮」，看起来像是那个窗格没渲染出来。

它响应的是 **`pointerdown` / `mousedown` 序列**：

```js
for (const type of ['pointerdown', 'mousedown', 'pointerup', 'mouseup']) {
  tab.dispatchEvent(new MouseEvent(type, { bubbles: true, cancelable: true, view: window, button: 0 }))
}
```

另有一条**验收时必须知道的**：同一个 group 里不活动的那个窗格，dockview 的默认渲染器
（`onlyWhenVisible`）**只把 DOM 从文档里移除、不卸载组件**。所以 `querySelector` 找不到它里面的
东西，但它的 React 状态、总线监听都还在——「切走再切回来，计数还在」是正确的，
「切走的那个窗格收不到总线事件」则不对。

### 【未解决】dockview 的标签经 CDP 一次都点不动，真实鼠标事件也不行

2026-09-09 验证类名前缀隔离时遇到的，**至今没有结论，先记在这里免得被忘掉**。

上面两条给的办法（dispatch `pointerdown/mousedown/pointerup/mouseup`、反复点到成功为止）
这一次**都没成功**。换成 CDP `Input` 域发**真实鼠标点击**——那是浏览器自己合成的、
`isTrusted` 为真的事件——**同样切换不了**。两个方向都试过（A→B 与 B→A），
四个事件的 `target` 每次都是 `.dv-tab`，坐标没有偏，活动标签就是不变。

最后是用状态栏的「打开窗格」菜单、经 focus 那条路径才切换过去——验证因此没有中断。

**没验证的部分**：人用鼠标点能不能切换，没人试过。所以现在说不出这是 dockview 的问题、
CDP 的问题，还是那一版外壳的问题。

**与那次的改动无关**：`GwbTab.tsx` 一行没改，类名前缀隔离也不涉及标签条。哪天人用鼠标点也切换不了，
再当成真正的问题来查。

**2026-09-09 第二轮（其余四个插件全部迁移那次）没再遇到**：四个窗格全部经状态栏的「打开窗格」
菜单激活成功，验证顺利。所以这个现象**不能稳定复现**，而**人用鼠标点能不能切换
仍然没人试过**——两个未知都还在，这条继续保留为未解决。

## dockview

### 主题必须经 `theme` 选项传给它，加在 `<html>` 上没用

第三阶段最费时间的一条。dockview 主题样式表写好了、`<html>` 上加了 `dockview-theme-light
dockview-theme-gwb` 两个类，探针脚本读 `document.documentElement` 上的
`--dv-group-view-background-color` 是对的（`oklch(1 0 0)`），**可容器底部是一片深蓝黑**。

根因在祖先元素上：dockview 自己会把主题类名写到它内部的 `.dv-shell` 上，不传就是默认的
**`dockview-theme-abyss`**（一套深色主题）。那一层离元素比 `<html>` 近，整个覆盖了我们的值。

```
DIV.dv-shell dockview-theme-abyss …     ← 它把类加在这里,--dv-* 从这层往下都是 abyss 的
…
HTML.dockview-theme-light dockview-theme-gwb   ← 我们加的这份在外层,被覆盖
```

正确做法是传 `theme: { name, className, colorScheme }`。**`className` 一个字段可以写几个类**
——dockview 用 `classNames.split(' ')` 解析。

`<html>` 上那份保留作为备用，给可能放在 `body` 下的 portal 元素——多加一个只定义变量的类
没有代价，漏了的话那些元素整片没有样式，而且要拖动时才会发现。

**现在不再使用它自带的主题**，`className` 只有 `dockview-theme-gwb` 一个。这个问题本身没变：
**不经 `theme` 选项传入，`.dv-shell` 上就是 `dockview-theme-abyss`**——忘了传，症状照旧是容器底部一片深蓝黑。

### 它自带的 18 套主题一套都不用，所以那批变量得自己全部定义

不用它的主题，裁剪后剩下的基础规则引用的 **54 个 `--dv-*` 全由 `dockview-theme.css` 提供**
（样式表里实际定义了 71 个——多出来的是企业模块那批与我们自己的中间变量，**故意全部定义**，
维护一份「已知用不到」的例外清单只会越来越过时）。dockview 升级新增一个，我们就漏一个，而**漏了是
读到空值、不报错**——只是某个高度没了、某个交互没样式。

**升级 dockview 之后核对一遍**，一条命令就能做（在 `plugins/shell` 里运行）：


### 8.2.0 里标签之间那条分隔线，它自己的规则不生效

我们把 `--dv-tab-divider-color` 设成了 `--border`，实际测量 `::before` 的 `content` 是 `none`
——**线根本没画出来**。而规则确实在产物里（不是被我们裁掉的）：

```css
.dv-tabs-container.dv-horizontal .dv-tab:not(:first-child)::before { content: " "; … }
```

问题在选择器：**标签条的方向类已经改成了 `dv-tabs-container-vertical`**（水平方向不加
modifier），而 `dv-horizontal` / `dv-vertical` 现在只属于 split-view。那三条分隔线规则
匹配不上任何 DOM，**它自带 18 套主题里设置的 `--dv-tab-divider-color` 也就都不起作用**。
这是 dockview 自己的 bug，跟我们裁不裁样式表无关。

我们的标签样式是**矩形分割**——标签紧贴、方角，非活动标签与标签条底色相同，全靠这条线分开。
所以照它原本的意图重写了一遍，只换成能匹配的选择器（`.dv-tab` 的 `position: relative`
在基础规则里，不用我们写）。

通用的教训：**设置了变量不等于那条规则会生效**。测量时要测最终效果（`getComputedStyle(el,
'::before').content`），不能只测变量是不是空值——这次那 20 个变量一个都不是空值，线却没画出来。

### `addPanel` 遇到重复 id 会同步抛错，后果比「少开一个窗格」严重

`api.addPanel({ id })` 遇到已经存在的 id **同步抛 Error**（`_doAddPanel` 第一句就是这个
检查），不覆盖、不返回已有的那个。

第三阶段的 `onReady` 里直接调 `addPanel`，**没有预先检查、也没有 try/catch**。当时没出错只是因为
注册表的 Map 键 `(entryId, 窗格 id)` 在上游保证了不会有两条同键记录。而它一旦抛错：

1. `onReady` 是在 dockview-react 的 `useEffect(…, [])` 里**同步**调的，异常从 effect 里
   抛出 → React 卸载整棵树 → **白屏**
2. 那个 effect 的 `return () => api.dispose()` **从来没被返回**，DockviewComponent 连同
   它的 ResizeObserver 一起泄漏
3. `bootShell` 的 `.catch` 捕获不到——它捕获的是 `boot()` 那条 Promise，不是 React 渲染

所以开窗格只有一种做法：**先算好唯一 id 再 addPanel**，`onReady` 与 `openPane` 共用这一处。

另外查证并排除了一个顾虑：**panel id 不会写进 DOM**。tab 与 tabpanel 的 DOM id 是自增计数器
（`dv-tab-N`），dockview 全部源码里的 `querySelector` 查的都是 `.dv-*` 类名。所以 id 里用什么
字符都安全——用 `:` 作分隔的理由不是「怕 querySelector」，是「只用一种分隔符」。

另有一条**格式上的硬要求**：写到磁盘时 panel 表是**按 id 做键的对象**（`_doFromJSON` 里
`Object.keys(data.panels)`），所以序列化格式根本表达不出重复 id。实例 id 全局唯一不是
「最好这样」，是格式要求。

### 窗格 id 里不许有 `:`，否则查重会不报错地匹配到错的窗格

`entryId` 自己就带冒号（实际运行时是 `home:hello`），而面板 id 是 `plugin:<entryId>:<窗格 id>`。
窗格 id 里再有一个冒号的话，两组不同的「条目 × 窗格」能拼出同一个基名：

- `home:hello` + `main` → `plugin:home:hello:main`
- `home` + `hello:main` → `plugin:home:hello:main`

**有了实例查重之后这个问题反而更难查**：没有查重时 `addPanel` 当场抛错，现在查重把它当成
「已经开着」，不报错地追加一个 `:2`。人看到的是自己的窗格标题莫名多了个「(2)」，而源头
在另一个插件的注册参数里。

注册时直接拒绝，跟空 id 一样抛错，错误信息里带包名。

### 新建一组只切分基准组的一半：`addPanel` 两种写法都会改变别的组，新建分支时还会少算一份组间缝

开窗格要「把基准组对半分、别的组一点不变」。dockview 8.3.1 里 `addPanel` 带参照新建组的两种写法都做不到，
在隔离 home 里测过（视口 1086×683、组间缝 8，三组一排 495 / 295 / 265，切分中间那组）：

- **带参照带方向、不给尺寸**：`createGroupAtLocation` 用 `Sizing.Distribute`，同一排四组全部均分成 261 左右
- **给 `initialWidth`（基准组宽的一半）**：新组得到这个宽度，扣减的却是**这一排最右那组**——splitview 的
  `relayout` 从最后一个视图往前分配。基准组不变，最右那组 265 → 117。只有基准组本来就在最右时结果才碰巧正确

只切分参照组一半的是拖放那条路径：`moveGroupOrPanel` 给新组的尺寸是 `dropSizing` → `Sizing.Split`（源码注释
引 dockview 自己的 issue #1612）。所以外壳先把新窗格当**不激活的**标签开进基准组，再 `moveTo` 到它右边——
基准组 295 → 144 / 144，同一排的其他组各少 0.67px（多了一道缝，整排重新平均分配；逻辑尺寸没变，这一点避免不了）。

**还有一处**：基准组在一列里（上下叠放）时，向右切分要把它放进一个新的横向分支，而 `Gridview.addView` 创建分支时
设回去的尺寸是叶子节点**渲染后的高度**（`parent.size`，已经扣掉分摊的组间缝），不是它在那一列里的逻辑尺寸。
分支因此少了一份组间缝的分摊量，多出来的高度给了同一列的其他组：基准组 313 → 309，下面那组 314 → 318。
两种写法都会遇到。补救办法是切分后把基准组的高度设成「2×原高−现高」——`setSize` 会传递到外层那一列，
设置的正是分支的逻辑尺寸，渲染出来回到原高，多给出去的高度从同一列的其他组那里扣回。两组叠放、三组叠放时的
上中下位置，加上根节点是纵向的情况，六种布局测下来，其他组的宽高偏差都不到 1px。

### 产物测试的正则要锚定在行首，否则会被 dockview 自己的错误消息误导

shell 的产物测试第一次运行就报「`dockview-enterprise` 被打包进 client.js 了」。**实际没有**
——那个字符串出自 dockview 的一句错误消息，消息里嵌着一段示例代码：

```
  npm install dockview-enterprise

```

第一版正则在整个文件里找 `import '…'`，773KB 的 client.js 里什么文本都有。改成用 `^import` 锚定行首：

同一个测试文件里检查「dockview.css 不许有 scope 规则」的那条也出过类似的错：两张样式表**开头的

去掉注释。

## 组件与 shadcn CLI

### `components.json` 的 `tailwind` 是必填的，插件因此得有个样式入口

schema 的顶层 required 是 `style` / `tailwind` / `rsc` / `aliases`，而 `tailwind` 自己的
required 是 `config` / `css` / `baseColor` / `cssVariables`——**一个都不能省**。省了报的是
一句没有细节的 `Invalid configuration found in …/components.json`。

`tailwind.css` 得指向一个真实路径。插件本来没有 CSS 入口（构建输入由 `tools/build-styles.ts`
在内存里拼），所以补了一个 `src/client/styles.css`。**这不是工具强加的负担**——插件作者
本来就需要一个地方写自己的 CSS 规则，构建时把它 `@import` 到输入末尾。

Tailwind v4 下 `tailwind.config` 填空字符串（v4 没有配置文件了）。

### 别写 `baseUrl`——TS 7 把它移除了

{/* ref file="../plugins/baseui/tsconfig.json" lines="1-12" */}

shadcn 文档教的是 `baseUrl` + `paths` 那套旧写法，照抄会遇到
`error TS5102: Option 'baseUrl' has been removed`。TS 7 里 `paths` 直接相对 tsconfig
所在目录解析，把 `baseUrl` 删掉就行，别的不用改。

`@/` 别名一共要配三处，都指向 `src/client`：插件根的 tsconfig（**给 CLI 读**，它据此决定把
添加的组件放在哪）、`src/client` 那份（给 typecheck）、`build.ts` 里 esbuild 的 `alias`
（给打包）。

### 插件根少配那处 `paths`，CLI 会把组件放进一个**名字就叫 `@` 的目录**

上一条的三处里少配哪一处，多数在构建时就报错，不会拖到运行时——**插件根那一处例外**。

CLI 拿插件根的 tsconfig 去解析 `components.json` 里的 `@/components/ui`。插件根没有 `paths` 时
它**不报错、也不改用别的路径**，照字面建出一个目录：

```
plugins/logger/@/components/ui/button.tsx   ← 四个组件都放在这里
```

**症状**：CLI 正常输出 `✔ Created 4 files`，只是路径写的是 `@\components\ui\button.tsx`
——那一行是唯一的线索，而且很容易被当成别名的显示方式忽略掉。真正的报错要等到 typecheck，
说的是「找不到 `@/components/ui/button`」，跟根因隔着一层。

**修法**：插件根 tsconfig 补上 `paths`，删掉误建的 `@` 目录重新添加一次。写这个插件时就遇到了这个问题。

### 新版 shadcn 不再生成 `lib/utils.ts`，改用 `cn` 这个包

添加的组件第一行是 `import { cn } from "cn"`——那是 shadcn 官方发布的包
（`github.com/shadcn-ui/cn`，MIT），用来直接替代 clsx + tailwind-merge。
所以 **`lib/utils.ts` 没有了**，`clsx` 与 `tailwind-merge` 也不再需要。

CLI 把 `cn` 装进 **`dependencies`**。按本仓规则「打包进本插件产物的算 dev 依赖」要移到 devDependencies
——它会被 esbuild 打包进 `client.js`，留在 dependencies 只会让装这个插件的人多下载一份用不上的包。

### new-york 的组件大量使用 `animate-in`，样式入口不引入 `tw-animate-css` 它们就不生成规则、也不报错

`animate-in` / `fade-in-0` / `zoom-in-95` / `slide-in-from-*` 这一组类**不是 Tailwind 自带的**，
出自 `tw-animate-css` 那个包。而 shadcn 的 new-york 风格从 `dropdown-menu` 到 `dialog`
到处在用它们——样式入口里没引入这个包，Tailwind 就**一条规则都不生成**：类名照写、构建照样通过、
菜单永远没有动画。

**没有任何一处会报错**，因为「生成不出规则」在 Tailwind 看来跟「这不是个类名」是同一回事
（同一个性质在类名前缀隔离下的表现是漏写前缀的类不生效，见样式与组件的
[会静默失效的几种写法](/docs/styles#会静默失效的几种写法)）。

**用选择器限定范围（scope）的插件一直是这样，没人报告过**——`tools/build-styles.ts`（2026-09-09 已删除）
拼出的输入里也没有这一行，所以那些插件的菜单本来就没有过渡动画。是给 hello 写独立样式入口时
逐条确认「这行不引入会怎样」才发现的，不是出了问题才发现的。

样式入口开头的注释写明四行 import 一行都不能省，也写了它带出的那批全局规则无害：

{/* ref file="../plugins/baseui/src/client/styles.css" lines="2-3" */}

### CSS 注释里写 `--tw-enter-*` 时那个 `*/` 会提前结束注释，报错完全不指向根因

跟 TS 块注释里出现 `*/` 是**同一个问题的 CSS 版**，但症状更难认出。

`tw-animate-css` 带来十七个 `--tw-enter-…` `--tw-exit-…` 的 `@property`。开头的注释里想用通配符
写出这批变量名，写成 `--tw-enter-*`、后面紧跟一个 `/`，**那个 `*/` 当场结束了
`/* … */`**，注释的后半段变成了真正的 CSS。

报出来的是一句

```
Could not resolve value for theme function: theme(reference)
```

——**它指的是文件开头那几行 import，跟真正出错的地方隔着整段注释**。第一反应会去查
`theme(reference)` 是不是写错了、令牌的映射文件是不是没引入，而那里一点问题都没有。

修法跟 TS 那条一样：把通配的 `*` 换成省略号，别让 `*` 挨着 `/`：

{/* has file="../plugins/baseui/src/client/styles.css" text="--tw-enter-…" */}

**判据**：往块注释里写 glob、通配符、路径这类东西之前，先看一眼里面有没有 `*/`——
这条对 TS 和 CSS 一样成立，而 CSS 这边的报错更难定位。

### `group` 这类标记类也要带前缀，不带就永远匹配不上

把日志窗格迁到类名前缀隔离时遇到的（当时日志窗格还在 logger 插件里，前缀是 `logger:`）。日志行上加了
`group`、行里的来源名写 `logger:group-hover:…`——**类名都在、规则也生成了、就是不生效**，
鼠标移过去没有任何反应。

根因是 Tailwind 生成 `group-hover:` 规则时要引用那个**作为父级标记的类**，带前缀之后它引用的是带前缀的那个：

```css
/* logger:group-hover:text-foreground/90 编出来的 */
:is(:where(.logger\:group):hover *) { … }
```

父元素上要是写成不带前缀的 `group`，DOM 上就没有 `.logger\:group` 这个类，选择器**永远匹配不上**。

**没有任何一处会报错**——跟本页上面那条「不引入 `tw-animate-css` 就不生成规则」性质相同、表现不同：
这次规则生成了，只是它引用的类名和元素上加的类名不是同一个。

{/* ref file="../plugins/baseui/src/client/panes/logger/index.tsx" lines="301-303" */}

上下两段是一对：日志行上加 `baseui:group`，行里的来源名用 `baseui:group-hover:` 引用它，
**两边都带前缀**才对得上。

**判据**：凡是「一个类当标记、另一个类的变体引用它」的搭配——`group` / `peer` 这一类，还有
`group/<名>` 这种具名变体——两边一起带前缀。测试查不出这一条：`group` 本身在不带前缀编译时
也生成不出规则（它不是工具类，只是个标记），所以 `prefix.test.ts` 那条「能生成规则的就是
漏了前缀」的判据对它不起作用。

### lucide 图标上的 `.lucide` 类不是前缀隔离的漏洞

验证类名前缀隔离时在 DOM 里看到很多 `class="lucide lucide-chevron-down"`，第一反应是「有不带前缀的
类名漏出来了」。**不是。** 那是 lucide 写进 SVG 的**身份标记**，跟容器上的 `data-gwb-plugin`
性质相同：全站的样式表里**没有任何一条规则匹配 `.lucide`**，它只是给人和探针脚本一个
识别图标的标记。

**判断隔离有没有失效要看样式表，不看 DOM**：失效的定义是「产物里有一条不带前缀的类
选择器」，产物测试查的正是这个。DOM 上有一个没有任何规则匹配的类名，不会因此影响到
别的元素的样式。

**所以别顺手去掉它**（改 `iconNode`、加 `className` 覆盖都能做到）：去掉之后隔离一点没变强，
调试时反倒少了一个标记。反过来，**验证隔离时也别拿 DOM 里的类名清单当证据**——要看的是
`dist/*.css` 里的选择器。
