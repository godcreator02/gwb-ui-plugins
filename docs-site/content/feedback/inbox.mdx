## 2026-09-13 总控台会话：第一次开机后布局没有自动保存到磁盘（隔离 home 上连续三次开机）

来源：总控台会话（验证「新建桌面新建时为空」时遇到，shell 0.4.4 与 0.4.5-dev 都有这个问题）。

现象：`devkit.home.new` 启动的隔离 home（窗口从不进前台），开机按默认布局打开窗格之后，
**防抖保存从未执行**——`data/shell/layout.json` 不存在，`gwb.log` 里 `shell.layout.save`
只有「登记上了」没有一次执行。直到切桌面 / 新建桌面触发**同步 flush** 才第一次写进文件。
同一时段没有任何报错，状态栏也没有「布局没存上」（说明 promise 没走到失败分支，更像定时器
根本没触发）。

两个怀疑，还没区分出是哪个：

1. occluded 窗口的计时器节流——devkit 启动 home 时带了 `--disable-backgrounding-occluded-windows`，
   但这个开关阻止的是渲染层把窗口判为隐藏，`setTimeout` 节流是否也被阻止没查过
2. `onWellReady` 里订阅 `onDidLayoutChange` 排在 `openDefaults` **之后**——若 dockview 在
   `addPanel` 里同步发事件，打开默认窗格的那三次调用全发生在订阅之前，一个事件都收不到

复现：启动一个隔离 home → 什么都不动 → 读 `<home>/data/shell/layout.json`（没有）。
default home 平时看不见这条，因为人一操作（开、关、拖动窗格）就会产生订阅建立之后的事件，照常保存到磁盘。

区分两个怀疑的实验现在就能做：往 `onWellReady` 里订阅之后手动 `api.addPanel` 一次，看 `scheduleSave`
有没有触发——触发了就是怀疑 2，没触发就是怀疑 1。

## 2026-09-17 总控台会话：窗格容器的 data-gwb-plugin 取自布局文件，包改名后一直是旧名

来源：总控台会话（修 default 里「单元」窗格整片没有样式时查出来的；unit-folder 插件已在 0.6.0 改用类名前缀，
不再依赖这个属性，所以这边不急）。

现象：`PluginPane` 加在容器上的 `data-gwb-plugin={pluginKey}`，`pluginKey` 来自 dockview 面板 params，也就是
布局文件里保存的那份，不是当场查注册表。default 的 `shell.layout.get` 里，换 scope 之前开的窗格全都还是
`@godcreator02/gwb-*`（单元、日志、站内预览、站监控、外观、插件源），而 `entryId` 没变、窗格照样能挂载。
于是属性上的「身份」对不上现在的包名，谁也不报错。

影响：前缀方案下属性「只是身份标记」，样式不受影响；但注释里说它是给探针、样式调试「认插件的标记」，
这个标记在旧的布局文件上指向了错的插件。另外 `saved` 里那套叫「88」的布局引用的 plugins / hello / status 是早就不存在的插件。

建议（还没判断，供参考）：挂载时用 `fetchPaneModule` 返回的当前包名覆盖 params 里那份；或读布局文件时按
`entryId` 把 `pluginKey` 更新成当前值，在下次保存时一并写回文件。

复现：`shell.layout.get` 看任何一个换 scope 之前开过的窗格的 `params.pluginKey`。

## 2026-09-24 要跟插件管理 0.9：用到的插件改写进 peer，list 换成 unmetPeers，update-all 回执加 dependents

来源：总控台会话（devkit 仓规格「插件之间写 peer」，插件管理 0.9.0 与 devkit 0.18.15 同一批发布）。

插件管理 0.9.0 是破坏性版本，baseui 的 dev 写的 `^0.8.0` 在它发布后就不在范围内，下次发版 `devkit.release` 会拒绝。要做的：

1. **依赖改写法**：插件用到的别的插件（经 `ctx.inject` 用它的服务、或 import 它的类型）写进 `peerDependencies`，
   写 `^<源上 latest>`；只是可选使用的在 `peerDependenciesMeta` 标 `optional: true`。dev 里不再写这些插件。
   baseui 对应：外壳 `@godcreator/gwb-shell` 必需，日志、插件管理可选。`devkit.release` 查 peer 里的插件与源上 latest
   在不在同一条线（0.x 比次版本号，≥1 比主版本号），不在就拒
2. **`plugin-manager.list`**：每个包的 `unmetRequires` 删了，换成 `unmetPeers: { pkg, range, installed? }[]`——插件 peer 里
   （内核包与 cordis 除外）home 里没满足的包：没装（optional 的没装不算）、或装着的版本不在范围里。没装时没有 `installed`。
   baseui 目前不读 `unmetRequires`，代码不用改；想在已装列表上标出来可以读这个字段
3. **`plugin-manager.update`**：回执有 `dependents: { pkg, entries }[]`——`pnpm add` 前后真实目录变了、本身没被升级的包
   （多半是 peer 写了被升级包的插件）会在升级的包重新加载之后一起重新加载，`entries` 与 `updated[].entries` 同形。
   `describeUpdateAll` 可以把它列出来；全都最新时是空数组
4. pnpm 由插件管理与 devkit 运行时一律带 `pnpm_config_auto_install_peers=false`，home 里没装的 peer 不会被自动装进来

规矩正本：devkit 文档站的依赖规则页与说明书 `gwb-release`。
